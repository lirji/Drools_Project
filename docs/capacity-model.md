# 活动容量评估：Drools / QLExpress / 纯 Java 各能扛多少活动

> **本文回答一个问题**：一个进程里挂 N 个营销活动，N 能到多大？分别用 Drools、QLExpress、纯 Java 三条路承载，
> 拿**同一份负载**实测出的足迹 / 编译耗时 / 决策延迟说话。
>
> 数据来自 `examples/capacity/CapacityBench.java`（可复跑，见 §7），以及仓库内既有的
> `ActivityKieBaseSizingTest` / `ActivityCapacityAcceptanceTest`（gated `-Dsizing=true`）。
> 本文是**活文档**；那份按时间点归档的 P0-5 内存模型见
> [`plans/activity-engine-platform-0718/50-P0-5-memory-capacity-model.md`](plans/activity-engine-platform-0718/50-P0-5-memory-capacity-model.md)。
>
> 引擎的**能力**差异（能不能做级联推理、TMS、CEP）不在本文范围，看
> [`interview/qlexpress-vs-drools.md`](interview/qlexpress-vs-drools.md) 与 [`drools-capabilities.md`](drools-capabilities.md)。
> 本文只谈**成本**：同样一件事，三条路各要花多少内存、多少 CPU。

---

## 0. 先给结论

单进程、每活动 1 条 3 叶资格条件 + 10 档阶梯（本项目的典型形状）：

| | 纯 Java（本项目现状） | QLExpress 3.3.4 | Drools 8.44.2 |
| --- | ---: | ---: | ---: |
| **每活动常驻足迹** | **1.8 KB** | **8.4 KB** | **~180 KB** |
| **每活动准备（编译）耗时** | 0（无编译） | ~1.3 ms | ~4.8 ms |
| **每候选决策成本** | ~0.18 µs | ~2.9 µs | ~12 µs |
| **1 GB 常驻预算能挂多少活动** | **~58 万** | **~12 万** | **~5,800** |
| **单次决策能同场多少候选**（P99≤50ms） | 不构成约束 | ~1.7 万 | **~1,000** |

**一句话**：同一件事，QLExpress 比纯 Java 贵 ~4.7×，Drools 比纯 Java 贵 **~100×**。
三者差的不是常数因子上的调优空间，是**量级**——所以「用哪个引擎」这个决定，
在活动数上到千级之后就不再是风格问题，而是能不能装下的问题。

**但这不等于 Drools 该被淘汰**：它贵在「把每条规则编译成类、建 RETE 网络」，
买到的是**规则之间的推理**（级联、撤销、优先级、增量匹配）。本项目的三类计算
（阶梯落档、折扣合并、条件树判定）都不需要其它规则的结论，所以这笔钱花出去买不到东西——
这正是主链路已经移出 Drools 的原因（见 §6）。

## 1. 怎么测的

### 1.1 负载定义（三条路**完全等价**）

每个活动 =

- **一棵 3 叶资格条件树**：`AND(orderAmount >= x_i, vipLevel >= y_i, channel IN [APP,H5])`，
  门槛逐活动不同（`x_i` 在 0~400 循环、`y_i` 在 0~3 循环），保证不同活动落在不同门槛上；
- **一条 T 档阶梯**：按 `orderAmount` 落档，区间 `[min, max)`，命中给固定奖励。

一次决策 = 对 N 个候选活动做资格判定，通过的再落档取金额、求和。

三条路的实现：

| 引擎 | 规则怎么表达 | 常驻的是什么 | 一次决策做什么 |
| --- | --- | --- | --- |
| **纯 Java** | 直接持有 `ConditionNode` 树 | N 棵条件树 + N 组档位 | 生产同款 `ConditionTreeEvaluator.matches()` + 线性扫档 |
| **QLExpress** | 条件树翻成等价脚本 | N×2 份预编译 `InstructionSet` | `runner.execute(instructionSet, ctx, …)` 循环 N 次 |
| **Drools** | 生产同款 `ActivityDrlBuilder` 生成 DRL | 2 个 `KieBase`（资格 / 阶梯） | 每个 KieBase 各起一次 `StatelessKieSession` + `execute` |

> **为什么这么比才算公平**：Drools 侧用的是**生产同款** `ActivityDrlBuilder`（`explain=false`，与热路径一致），
> 纯 Java 侧用的是**生产同款** `ConditionTreeEvaluator`，QLExpress 侧按它在生产里的标准用法
> （`ExpressRunner` 单例 + 指令集预编译常驻）。三条路都不含数据库、不含网络、不含 Spring，
> 测的是**纯引擎成本**。

### 1.2 等价性闸门（这份基准唯一的正确性保证）

三条路每个规模都算一个 checksum（所有命中活动的奖励之和）。**checksum 不一致 = 负载不等价 = 所有数字不可比**，
基准会直接打红。实跑结果：8 个规模 × 3 引擎全部一致（`N=10 → 15`、`N=1000 → 720`、`N=5000 → 3580` …）。

没有这道闸门，"引擎 A 比引擎 B 快 10 倍" 完全可能只是因为 A 少算了一半的活。

### 1.3 测量方法

- **足迹**：GC-delta 采样（连续 3 次 `System.gc()` + sleep，取 `HeapMemoryUsage.used` 与 `Metaspace` pool 的差）。
  测量前先用**与正式负载同形状**的小样本把三条路各走一遍（`warmupInfra()`），把
  「Drools 编译器 ~3MB Metaspace」这类**整进程一份**的一次性开销剥离出去——不剥的话 N=10 那一行会把它摊在
  10 个活动头上，得出「每活动 525 KB」这种假结论（见 §2 表格里 N=10 那行仍偏高的残留）。
- **延迟**：warmup 后采样，取 p50 / p99。大 N 自动降采样（单次决策本身就贵，跑满 300 次只是拖时间，不增信息量）。
- **机器**：本机 macOS / JDK 21.0.11 / G1 / `-Xmx4g -XX:MaxMetaspaceSize=1g`，2026-08-10 实跑。
  **绝对值随机器波动，稳健的是各引擎之间的比例关系**，不是具体数字。

**读表要点**

1. **每活动足迹很快收敛成常数**：Java 1.8 KB / QLExpress 8.4 KB 从 N=50 起就纹丝不动，
   Drools 从 N=100 起稳在 ~180 KB。N=10 那三行偏高，是一次性基础设施的残留，不代表边际成本。
2. **Drools 有 1/3 的足迹在 Metaspace**（每个 KieBase 自带 classloader，规则编译成类）。
   这条最容易在生产上翻车：**不配 `-XX:MaxMetaspaceSize` 就是无上界**，涨爆的是原生内存，比堆 OOM 难诊断得多。
   Java 与 QLExpress 侧的 Metaspace 增量在 N≥200 后基本为 0——它们**不生成类**。
3. **Drools 的 p99 在 N≥2000 之后失控**（207 ms / 529 ms，相对 p50 是 7.7× / 8.5×）。
   那不是规则求值慢，是这一档规模下 GC 压力已经进了尾延迟。**p50 还能看的时候 p99 已经不能用了**，
   容量线要按 p99 划，不能按 p50 划。

### 2.2 档位边界是否跨活动共享（Drools 的 alpha 节点复用测试）

主表里所有活动共用同一组档位边界（`[0,100)`、`[100,200)`…），理论上 Drools 的 alpha 网络能
**跨活动复用节点**：一千个活动的 `orderAmount >= 100` 只建一个节点。这会不会让 Drools 的数字好看得不真实？

`-Dbench.distinctTiers=true` 把每个活动的档位边界逐一错开，打掉复用后重测（N≤1000）：

| N | Drools 合计 (KB)：共享档位 | Drools 合计 (KB)：逐活动错开 | 差异 |
| ---: | ---: | ---: | ---: |
| 100 | 18064 | 15784 | −12.6% |
| 200 | 35816 | 29970 | −16.3% |
| 500 | 106217 | 101114 | −4.8% |
| 1000 | 176706 | 173706 | −1.7% |

**结论：差异在噪声内，而且方向还相反。** 也就是说 Drools 的足迹**不是**被 alpha 节点复用决定的——
主导项是「每条规则编译出的类 + 该规则自己的 RETE 节点」，这部分不管边界共不共享都得付。
所以 §3 的 ~16 KB/规则 这个系数对「运营各配各的档位」同样成立，不需要打折。

> 这是一条**被证伪的假设**，保留在文档里是因为它值钱：下次有人问「把档位对齐是不是能省内存」，
> 答案是不能，别去做那个优化。
> 顺带，Java 与 QLExpress 两条路在两种模式下数字几乎不变（它们没有节点共享这回事）——这本身就是负载生成没跑偏的自校验。

### 2.3 档位数敏感度（`T̄` 是所有引擎的共同放大器）

固定 N=1000，只改每活动的档位数：

| 每活动档位 T̄ | 纯 Java (KB/活动) | QLExpress (KB/活动) | Drools (KB/活动) | Drools 生成规则数 | Drools (KB/规则) |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 0.5 | 2.6 | 49.7 | 2,001 | 24.8 |
| 10 | 1.8 | 8.4 | 176.7 | 11,001 | 16.1 |
| 20 | 3.2 | 14.7 | 312.6 | 21,001 | 14.9 |

三条路**都**随档位线性增长，但斜率差两个量级：每加一档，Java 付 0.14 KB、QLExpress 付 0.63 KB、
Drools 付 **13.8 KB**（因为 Drools 是**每档一条独立 rule**，而另两条路是同一个数据结构里多一项/多一个 if 分支）。

> ⚠️ 这里推翻了一个直觉上很顺的猜测：「QLExpress 把整条阶梯编译成**一份** if 链指令集，
> 所以它的足迹应该和档位数基本无关」。**实测不是**——指令集本身随 if 分支线性变长，
> 1→20 档时每活动从 2.6 KB 涨到 14.7 KB（5.7×）。猜测和实测差得足够远，
> 所以这一节是量出来的，不是推出来的。

## 3. 容量公式

### 3.1 常驻足迹

设 `N` = 活动数，`T̄` = 平均档位数。

按 §2.3 的三个档位点线性拟合（`每活动足迹 = base + slope × T̄`），三条路都拟合得很紧：

```
纯 Java     ≈ (0.36 + 0.14 · T̄) KB × N
QLExpress   ≈ (2.0  + 0.63 · T̄) KB × N
Drools      ≈ (36   + 13.8 · T̄) KB × N   ≈ 16 KB × 生成规则数 = 16 KB × N × (1 + T̄)
```

代回校验（实测值在括号里）：

| T̄ | 纯 Java | QLExpress | Drools |
| ---: | ---: | ---: | ---: |
| 1 | 0.50 (0.5) | 2.63 (2.6) | 49.8 (49.7) |
| 10 | 1.76 (1.8) | 8.30 (8.4) | 174 (176.7) |
| 20 | 3.16 (3.2) | 14.6 (14.7) | 312 (312.6) |

Drools 的 `16 KB/规则` 由主表反推：`176706 KB ÷ 11001 规则 = 16.1`，在 N=200~5000 区间稳定
（16.3 / 19.3 / 16.1 / 16.0 / 19.4）。

### 3.2 和生产 weigher 常数的关系（重要，别改错）

`ActivityRuleRuntimeService` 的缓存权重用的是 **`260 KB + 37 KB × 规则数`**，比这里实测的 16 KB/规则**保守 ~2.3 倍**。
两个数字都对，差别在**KieBase 的形状**：

| 形状 | 每 KieBase 规则数 | 实测每规则足迹 | 出处 |
| --- | ---: | ---: | --- |
| 每租户/场景一个小 KieBase（**生产形态**） | 1 ~ 200 | ~33 KB | `ActivityKieBaseSizingTest`（本机 2026-08-10 复跑：200 档 → 4291 堆 + 2404 Meta = 33.5 KB/规则） |
| 所有活动打包进 2 个大 KieBase（本基准） | 2000 ~ 55000 | ~16 KB | 本文 §2.1 |

每个 KieBase 都要付一份 classloader + 基础结构的固定开销；规则少时这份固定开销摊得贵，规则多时摊薄，
到 ~2000 条以上收敛在 16 KB/规则。**生产是前一种形态**（cache key 含租户，天然按 (tenant, bizLine, scene) 分片），
所以 37 这个常数是对的，而且方向是**保守**（宁可早淘汰，不可吃爆堆）。

副作用要知道：用 256 MB 的 `cache-max-weight-kb` 预算时，**按权重记账记满了，实际字节可能只用了 ~110 MB**。
这是有意为之的安全裕量，不是 bug；真要压榨这块内存，前提是先把生产的 KieBase 形状固定下来并重新标定，
**不要只改常数**。

### 3.3 准备（编译）吞吐

```
Drools      ≈ 0.44 ms / 规则  →  ≈ 4.8 ms / 活动（T̄=10）
QLExpress   ≈ 0.67 ms / 指令集 →  ≈ 1.3 ms / 活动
纯 Java     ≈ 0（只是构造对象）
```

这条决定**发布/热更新窗口**，不决定稳态。1000 个活动全量重编译：Drools 4 秒、QLExpress 1.4 秒、Java 0。
本项目已经把这段挪出热路径（decision 侧发布代际轮询到新代 → 后台线程建快照 + 独立编译池预热 → 就绪后原子切指针），
所以这几秒不落在用户请求上——但它决定了「发布后多久新活动才真正生效」。

### 3.4 单次决策延迟

```
纯 Java     ≈ 0.18 µs / 候选
QLExpress   ≈ 2.9  µs / 候选
Drools      ≈ 12   µs / 候选（且 N≥2000 后 p99 相对 p50 劣化到 8×）
```

## 4. 「能支持多少量级的活动」——分三条约束线看

「多少活动」其实是**两个不同的问题**，混在一起谈必然得出错误结论：

- **(a) 平台总共能挂多少活动** —— 受**内存**和**编译吞吐**约束；
- **(b) 一次决策能让多少活动同场竞争** —— 受**延迟**约束。

本项目里 (b) 被数据库先筛过（按 SPU 绑定 / 业务线 / 状态取候选），典型候选数是**几十**，
所以真正的天花板是 (a)。但换个场景（比如"全站通用券"人人可参与）(b) 就会变成主约束。

### 4.1 约束线 A：常驻内存

用 §3.1 的拟合式换算（`活动数 = 预算 ÷ 每活动足迹`）：

| 常驻预算 | 纯 Java（T̄=10） | QLExpress（T̄=10） | Drools（T̄=10） | Drools（T̄=1，无阶梯） |
| --- | ---: | ---: | ---: | ---: |
| 64 MB | ~36,000 | ~7,800 | **~370** | ~1,300 |
| 256 MB（本项目默认 `cache-max-weight-kb`） | ~145,000 | ~31,000 | **~1,480** | ~5,300 |
| 1 GB | ~580,000 | ~125,000 | **~5,900** | ~21,000 |
| 4 GB | ~230 万 | ~50 万 | ~23,700 | ~84,000 |

> Drools 那两列要额外配 `-XX:MaxMetaspaceSize`（约占足迹的 1/3）。**不配 = 无上界**。

### 4.2 约束线 B：单次决策延迟

按热路径 P99 预算划线（决策服务的现实预算通常是 20~50 ms，还要留给取数和网络）：

| P99 预算 | 纯 Java | QLExpress | Drools |
| --- | ---: | ---: | ---: |
| 10 ms | ~55,000 候选 | ~3,400 候选 | **~600 候选** |
| 50 ms | ~270,000 候选 | ~17,000 候选 | **~1,000 候选**（N=1000 实测 p99 已 16 ms；N=2000 直接跳到 207 ms） |

Drools 这一列不是线性外推——它在 N=1000~2000 之间有个**悬崖**（p99 从 16 ms 跳到 207 ms）。
容量规划要按悬崖前划线，**不能按 p50 的线性趋势外推**。

### 4.3 约束线 C：发布窗口

「改了活动，多久生效」= 全量重编译时间（本项目走后台预热，所以是**生效延迟**而非**停机时间**）：

| 活动数 | 纯 Java | QLExpress | Drools |
| ---: | ---: | ---: | ---: |
| 100 | ~0 | 0.16 s | 0.7 s |
| 1,000 | ~0 | 1.4 s | 4.0 s |
| 5,000 | ~0 | 6.7 s | 24 s |

Drools 到 5000 活动时单次全量重编译 24 秒——这已经不是"预热"而是"重启级别"的操作了，
必须配增量编译（只重编受影响的 artifact）或分片 KieBase，不能全量重来。

### 4.4 综合答案

| | 舒适区（三条线都宽裕） | 需要认真设计（要分片/限档/异步预热） | 换引擎的分界 |
| --- | --- | --- | --- |
| **Drools** | **≤ 500 活动** | 500 ~ 2,000 | **> 2,000 就别硬扛**（内存 350 MB+、p99 已进百毫秒、全量编译 8 秒+） |
| **QLExpress** | **≤ 10,000 活动** | 1 万 ~ 10 万 | > 10 万（内存 800 MB+、全量编译 1 分钟+） |
| **纯 Java** | **≤ 10 万活动** | 10 万 ~ 100 万 | > 100 万（此时瓶颈早就不在引擎，而在取数与分发） |

**再压一句**：把「活动数」换算成规则数才是 Drools 的真实标尺。
`生成规则数 = N × (1 + T̄)`，**档位数比活动数更值得在运营侧收紧**——
10 个活动各配 200 档，和 2000 个活动各配 1 档，对 Drools 是同一个价钱。

## 5. 到了拐点怎么办（按代价从低到高）

1. **限档位，不是限活动**（零成本）。运营侧对 `T̄` 设硬上限。足迹是 `N × (1+T̄)` 的线性函数，
   砍档位和砍活动等效，但砍档位对业务的伤害小得多。
2. **按 (租户, 业务线, 场景) 分片 KieBase + LRU 淘汰**（本项目已做）。常驻的只是**热**租户，
   冷租户按需编译。代价是冷启动尖刺，要配预热和 single-flight（本项目用 Caffeine 的
   `get(key, mappingFunction)` 天然拿到 single-flight）。
3. **把不需要推理的计算移出规则引擎**（本项目已做，见 §6）。这是收益最大的一步——直接省掉 ~100×。
4. **水平扩进程**。决策服务无状态（快照 + 只读账号），加实例即可。注意每个实例都要**各自**
   常驻一份规则物料，内存是乘法关系，不是除法。
5. **换引擎**。到这一步说明前四条都不够，此时应先确认规则之间**确实需要推理**——
   如果不需要，换成表达式引擎或纯 Java 是纯赚；如果需要，那就得接受 Drools 的价钱并靠分片扛。

## 6. 回到本项目：这份数据支持了哪个决策

本项目的决策主链路**默认不进 Drools**（见 [`../CLAUDE.md`](../CLAUDE.md) 的「决策链路现状」）。
当时的判据是定性的：**「这条规则需不需要*其它规则的结论*」**——

- 阶梯落档 = 标量分段函数；
- 折扣合并 = 一次 reduce；
- 资格条件树 = 单事实布尔谓词。

三者都不需要，于是移出规则引擎。这份基准给那个定性判断补上了量化后果：

| | 移出前（Drools） | 移出后（纯 Java） | 差 |
| --- | ---: | ---: | ---: |
| 每活动常驻 | ~180 KB | 1.8 KB | **100×** |
| 每候选决策 | ~12 µs | ~0.18 µs | **67×** |
| 1000 活动的发布重编译 | 4.0 s | ~0 | — |
| Metaspace 风险 | 有（每 KieBase 一个 classloader） | 无 | — |

另外值得记的一条：`ConditionTreeEvaluator` 的类注释里写了**为什么当初没引 QLExpress**——
条件树已经以结构化 JSON 存在库里（`activity_condition.condition_tree_json`），**手里本来就有 AST**，
再把 AST 编译成字符串、引一个引擎去解析那个字符串是绕远路（多一个依赖、多一层翻译、多一个转义面）。
这份基准给那个判断也补了个价签：绕这一圈的成本是 **4.7× 内存 + 16× 决策 CPU**，换回来的是零。

**表达式引擎的价值在「让非开发者写逻辑」**——而这里运营写的是条件树，不是表达式，那份价值在此处不存在。
如果哪天需求变成「运营要写自由表达式」，QLExpress 的价签（8.4 KB / 活动、2.9 µs / 候选）是完全可以接受的，
届时它是正确选择。

### 什么时候仍然该上 Drools

这份数据**不是**「Drools 不好」的证据，是「Drools 用错地方很贵」的证据。以下场景它的价钱花得值：

- 规则之间**真的**互相影响：A 的结论改变 B 是否成立（级联、撤销 / TMS、优先级仲裁）；
- 事实会被规则**改写**并触发重新匹配（`modify` / `update` 语义）；
- 需要**增量匹配**：工作内存长期驻留、事实持续小步变化（CEP 滑窗风控是典型）；
- 规则数不大但**逻辑纠缠**：保险核保、信贷授信、复杂计费——几百条规则互相引用，手写 Java 会烂成一团。

选型决策树见 [`drools-capabilities.md`](drools-capabilities.md)，场景定位见 [`drools-use-cases.md`](drools-use-cases.md)。

## 7. 复跑

```bash
# 三引擎容量基准（默认规模 10 50 100 200 500 1000 2000 5000，每活动 10 档）
./examples/capacity/run.sh

# 只跑几个规模 / 改档位数 / 打掉 Drools 的 alpha 节点复用
./examples/capacity/run.sh 100 1000
TIERS=20 ./examples/capacity/run.sh 100 500 1000
DISTINCT_TIERS=true ./examples/capacity/run.sh 100 500 1000

# 仓库内既有的 Drools 足迹实测（gated，不进常规 ./mvnw test）
./mvnw -pl activity-common test -Dtest='ActivityKieBaseSizingTest,ActivityCapacityAcceptanceTest' \
  -Dsizing=true -DargLine="-Xmx2g -XX:+UseG1GC -XX:MaxMetaspaceSize=512m"
```

`examples/capacity/` **刻意放在 Maven 源码根之外**（沿用 `examples/aviator/` 的先例）：它引 QLExpress，
而生产四个模块都不该有这个依赖，也就不该让它进 reactor 的 pom。`run.sh` 会自己
`dependency:get` 拉 QLExpress 3.3.4 并拼 classpath。

## 8. 这份评估**没有**覆盖的

诚实列出来，免得被当成比实际更强的结论用：

- **只测单进程、单线程决策**。没测并发下的锁竞争与 GC 交互——Drools 的 `StatelessKieSession`
  是每次 new 的，高并发下的分配压力本文没量化。
- **没测多租户分片下的真实驻留曲线**。本基准把所有活动塞进 2 个 KieBase；生产是按
  (租户, 业务线, 场景) 分片 + LRU，热租户集合的漂移会带来冷编译尖刺，那条曲线要用生产流量画。
- **QLExpress 只测了 3.3.4**。4.x（`Express4Runner`）是重构版、API 不兼容，足迹与吞吐没测。
- **没测 Drools 的增量编译**。全量重编译 24 秒（5000 活动）是上界，实际发布只重编受影响的 artifact 会好很多。
- **绝对值绑本机**。换机型/JVM 要重新标定；跨引擎的**比例**比绝对值稳健得多。
