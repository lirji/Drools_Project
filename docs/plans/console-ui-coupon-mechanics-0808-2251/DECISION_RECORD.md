## 背景

用户给了四个设计参考站并要求「做炫酷一点的」：

| 参考 | 可抓取性 | 用法 |
|---|---|---|
| SaaS Interface | ✅ 抓到模式分类 | 直接对照缺口（见下） |
| Dribbble Dashboard 搜索 | ❌ JS 渲染 | 按其代表语汇：数据密度与图表表现力 |
| Land-book | ❌ 403 | 视觉完成度与留白节奏 |
| Mobbin | ❌ 需登录 | 真实产品的交互模式与流程完整度 |

SaaS Interface 的模式分类与控制台缺口几乎逐条对应，成为屏目清单的依据：

| 该站的模式 | 控制台现状 |
|---|---|
| Builder/Editor · Forms | `EditorView` 536 行硬编码表单 |
| Lists & Tables · **Filters · Bulk Actions** | 有搜索/状态筛选，**无批量操作** |
| Item Details · **Side Panel** | 详情是跳页，丢失列表上下文 |
| **Activity Feed** | 无。正是发布时间线的载体 |
| **Dashboard** | 无任何数据可视化（对应后端 D7 零指标） |
| Onboarding · Empty State | 有 EmptyState 组件，无玩法模板引导 |

## D1 · 松开「不推翻 tokens.css」这条约束

**决策**：允许改既有 token 的**值**（不改变量名），把 Calm Precision 演进成票券工学。

**此前立场**：上一轮我把「复用 tokens.css，只加不改」列为硬约束——理由是那套体系已实算过 WCAG，推翻等于把前一次 UX 重设计的账重付一遍。

**改变理由**：用户明确说「做炫酷一点的」。设计优先级是 **用户的话 > 项目既有系统 > 我的选择**。既有 token 体系的结构（四层面 / 语义色分离 / 三态主题 / 间距字号 scale）完整保留，换的是**值**与**形制**。

**代价与边界**：
- 所有组件都只 `var()` 引用 token，改值不改组件源码——这是既有体系的红利，本次直接吃到。
- 唯一需要逐组件扫的是 `--fw-medium:500` 在含中文元素上的用法（约 6 处）。按 CJK 只有 400/700 可靠的规矩，要么改 700 要么改 400。**建议作为独立小 PR 先落，与视觉方向解耦。**
- token 换代与结构改造**永不混在同一个 diff 里**（评审点名）。

## D2 · 选「票券工学」，否决另外三个方向

**决策**：以票券工学为骨架。3 位评委中 2 位选它。

### 评委原话（视觉冲击视角）

> 它是四张图里唯一一张放进作品集不会被认成「某某分析平台的截图」的——因为没有别的 B 端控制台长这样。它的冲击力来自形制而不是发光，所以是四家里最耐看的那种「炫酷」；**黑白测试全项通过**；而且它是唯一一个把最难的第 3 屏（动态权益编辑器）从 key-value 泥潭里捞出来的方向。

### 被否方案

| 方向 | 主张 | 否决理由 |
|---|---|---|
| **暗房信号台** | 深色暗房，发光编码信息（亮度=离阈值多远、模糊=离你多远） | ① **身份级硬伤**：`--accent #ff6ad0` 与 `--err #ff6b76` 在深色下是两个高明度粉红（hue 320 vs 356），它自己的示例里同一行同时出现品红占比条与朱红回退率——「强调色永不出现在状态位」这条自定规则被自己的示例推翻，而误读恰好发生在会静默改金额的头号指标列 ② 扫光每 15 秒对「刚更新」的行放一次，大促当天几乎每行每轮都在变，整表持续闪烁 |
| **示波指挥台** | 深色仪表舱，常驻实时信号带 | ① **致命**：常驻信号带没有数据源，且钉在六屏页头 = 六屏同时被一个不存在的 API 阻塞 ② 营销运营对决策吞吐 QPS 没有任何操作杆（那是 SRE 指标），它吃掉编辑器上最贵的垂直空间，是全组「工程师觉得很酷但运营根本不会点」的头号样本 ③ `.pulse 2.4s infinite` 挂在每个生效中行首，一屏十来个常驻呼吸光源 |
| **精密刻度** | 瑞士网格，冲击力来自秩序 | ① **自毁核心承诺**：为守住配额把 `--blue` 指向 `--accent`，于是信息态 Badge 与「当前选中/主数据序列/焦点环」共用同一个钴蓝，「看到彩色就意味着看到数据或状态」这条根规则塌掉 ② 唯一签名「刻度栏 rail」在 ≤1023px 下 `display:none`——平板与手机上这个方向没有任何可辨识特征 ③ 全站分区押在 `--rule-faint #eff0f3` on `#ffffff`（约 **1.03:1**），在常见办公 TN 面板上直接看不见 |

> 精密刻度虽落选，但它的**四档线权重制度**、**`--hairline` 双档**、**表格 `ch` 定宽 + sticky 操作列**、**账簿五行线**被整体并入终版（见 D4）。

## D3 · 「炫酷」在 B 端的兑现方式

**决策**：炫酷 = **形制 + 密度 + 精度**，不是发光与玻璃。

写进规范的反向验收清单（原型里不许出现）：

> 玻璃拟态、任何 `backdrop-filter`、彩虹渐变、粒子/极光背景、大于 10px 的圆角、emoji 图标、数字滚动动画、**静止状态下的任何循环动画**、居中 hero 区、卡片左侧强调色条。

正向的七项验收（少一样都算没做到）：齿孔撕线的真实感 / 甘特条的跨行对齐 / 量筒的临界线关系 / 票据金额排版 / 密度切换的密度感 / 越阈的斜纹 / 签名色的稀缺（全屏 <4%）。

最后一条自检写在规范末尾：

> 把六屏截图并排贴墙、蒙掉标题。有人问「这是 Grafana 还是 Datadog」= 失败；有人问「这是什么产品，我没见过」= 成功。

## D4 · 从落选方向嫁接的做法

| # | 嫁接内容 | 来源 | 理由 |
|---|---|---|---|
| G1 | `--hairline:1px` + `@media (min-resolution:2dppx){0.5px}` | 精密刻度 | 两行成本，整站质感抬一级 |
| G2 | 四档线权重制度（`--rule-faint` / `--border` / `--border-strong` / `--rule` 2px） | 精密刻度 | 但 `--rule-faint` **不许**用 `#eff0f3`（1.03:1），浅色最低取 `#e3e5ea` |
| G3 | 账簿五行线 `tbody tr:nth-child(5n) td{border-bottom-color:--rule}` | 精密刻度 | 密排表横向追踪的最便宜解 |
| G4 | 表格 `table-layout:fixed` + `ch` 定宽数值列 + 操作列 `sticky right:0` | 精密刻度 | 横滚时不丢操作；auto 布局下长中文活动名会让列宽跳动 |
| G5 | 留白四值语义化（`--gap-inline/group/block/section` = 8/16/32/64） | 精密刻度 | 配套定律：1px 线可替代 32px 留白，但不能替代 64px |
| G6 | 密度切换只改行高不改字号；`(pointer:coarse)` 强制回落 | 示波指挥台 | 触控下不允许真紧凑 |
| G7 | reduced-motion 补 `animation-iteration-count:1` | 暗房信号台 | 现状 `animation-duration:.001ms` 遇 `infinite` = 每毫秒重放的隐形 CPU 火炉 |

## D5 · 评审点名的致命项与修法

以下每条都是评委在 proof 里抓到的、会在真实浏览器里出错的问题。原型已逐条修掉。

| # | 问题 | 修法 |
|---|---|---|
| X1 | **抽屉阈值写成 `max-width:1023px`** —— `e2e-tablet-smoke` 在 768×1024 下**不点汉堡直接** `click(tenant-chip-acme)` 与 `click(tab-new)`，侧栏一旦离屏两个点击全部超时 | 改回 `max-width:767px`。这是本方向唯一一处已知的兼容性缺口，方向自己在 feasibility_notes 里承认了，但交上来的 proof 没改 |
| X2 | **密度切换绑在 `body:has(#d-compact:checked)`** —— `position:fixed` 的侧板/模态/Toast 在该子树之外拿不到变量；偏好无法持久化；`:has()` 在 Firefox <121 静默失效 | 改 `<html data-density="compact">` + localStorage |
| X3 | **齿孔缺口写死 `background:var(--bg)`** —— 同一个 Seam 出现在三种上下文（页底 grain 网纹 / 券卡白底 / 模态），写死三种里错两种，而这是头号签名手法 | 改 `var(--notch-bg, var(--bg))`，由使用点传入 |
| X4 | **甘特条共享时间轴的数学不成立** —— proof 里 07-05→10-31（4 个月）画成 36% 宽、11-08→11-09（2 天）画成 16% 宽，同一根 178px 轴上二者不可能同时正确 | 轴域钉死 `今天−60d / +30d`，位置由日期**可编程算**，段最小可视宽 6px，越界端画截断箭头。原型八行游标严格落在同一条 66.67% 垂直线上 |
| X5 | **`--seam` 对比度不足** | 浅色由 `#a9b8b5` 提到 `#8fa19d`（≥3:1），否则撕线在廉价屏上等于普通虚线 |
| X6 | **TierRuler 被排到落地第 6 步** —— 它同时是题面点名的成败关键屏的唯一解法，也是最贵的单个控件 | 实施顺序改为 **PR-4，排在工作台之前**。理由：它是唯一后端契约完整的屏（`field-dict` + `preview` 都已存在） |
| X7 | 主按钮在深色下文字可读性 | 引入 `--on-accent` token 由主题承担，不写死颜色 |

### 跨方向共性问题（四家都犯，一并修掉）

| # | 问题 | 修法 |
|---|---|---|
| X8 | **`thead th{position:sticky}` 放进 `overflow-x:auto` 容器** —— 按 CSS Overflow 规范，一轴非 visible 会让另一轴计算成 auto，容器变成滚动盒，sticky 相对它而非视口定位，**四家的表头贴顶全部不生效** | 给滚动容器显式 `max-height` + `overflow:auto`，让 sticky 有意义；表头背景必须是不透明 token |
| X9 | **右侧详情板一律占 `--z-drawer:900`**，与 `<768` off-canvas 侧栏同级，同时打开时由 DOM 顺序决胜负 | 新增 `--z-panel:880` |
| X10 | **侧板没接 `useScrollLock`**，且没处理跨断点 —— 一次「1000px 开侧板 → 拖到 1400px」会把 `body.style.overflow='hidden'` 永久留下 | 挂 `matchMedia('(min-width:1024px)')` 的 change 监听，跨过即解锁 |
| X11 | **grid 轨道写裸 `1fr`** —— 默认是 `minmax(auto,1fr)`，一个长中文活动名就能撑破轨道导致 body 横滚 | 一律 `minmax(0,1fr)`，写进 review checklist |
| X12 | **指望 `body{overflow-x:hidden}` 让溢出断言变绿** —— html 为 visible 时 body 的 overflow 传播到视口、body 自身计算回 visible，`document.body.scrollWidth` 仍含溢出，`e2e-phone-smoke` 照样红 | 真正的闸只有：`minmax(0,1fr)` + 宽内容各自 `overflow-x:auto` + 抽屉用 transform 离屏 + 伪元素动画不用 translateX |
| X13 | **焦点环从 outline 改 box-shadow**，理由写「`overflow:auto` 会裁 outline」 | 事实相反：`overflow` 裁掉所有绘制内容，box-shadow 同样被裁，而 outline 不占布局也不被裁——这正是 `tokens.css:154` 注释写明的理由。**保留 outline** |
| X14 | **SVG 展示属性里用 `var()`**（如 `fill="var(--err-soft)"`）—— 在 WebKit 会被判非法整体丢弃 | 全部改走 CSS 类。原型里 `<pattern>` 内部也照此处理 |
| X15 | SVG path 被容器横向拉伸时线宽与 dasharray 跟着变形 | `preserveAspectRatio="none"` + `vector-effect="non-scaling-stroke"`；坐标轴标签画在 **SVG 之外的 HTML** 里 |

## D6 · 诚实性：不用假数据糊弄

**决策**：屏 5、屏 6 在接口就绪前**不画假图**，显示说明卡：

> **决策指标尚未接入**
> 决策进程的耗时、命中率与回退率目前只在 Prometheus（`:9090`）中可见，控制台还没有对应的聚合接口。
> 待建接口：`GET /decision/v1/metrics`

原型里做成一个**可切换的开关**，让评审看到我们准备了降级态。导航项对应加 `--text-faint` 的「未接入」小标。

同源的三处诚实设计：
- 每人限领输入框**置灰** + 「本期为声明式，决策不扣减」（对应重构计划 DECISION_RECORD D5 选 B）
- 玩法模板屏四个玩法标灰并写明缺什么（第二件半价缺行项单价、秒杀缺一口价形态、定向券只有枚举位、加价购需两阶段决策）
- 沙盘/看板顶部标注数据来源

## 附：原型交付物

单文件 HTML，六屏 hash 路由（`#/bench` `#/templates` `#/editor` `#/sandbox` `#/monitor` `#/release`），数据写在顶部 `DATA` 常量六屏共读，时间基准钉死 `2026-11-06T15:44+08:00`。

**六项硬交互全部真做**：主题三态循环 / 密度切换（localStorage 持久）/ TierRuler 拖拽 + 键盘（人话预览与票据表实时联动、重叠出斜纹与错误文案）/ 行点击开侧板（三档响应式 + 跨断点解锁滚动）/ 批量四段流程（跨页选择 → 影响摘要 → 部分失败回执 → 10s 撤销）/ 排序三态 + 筛选 + 搜索组合。

发布前跑了 32 项自动校验（反向验收禁止项、致命项修复、七项炫酷兑现、六屏路由与硬交互），全绿。

### PR-4 权益编辑器核心控件 — 完成（TierRuler + 人话预览）

**替代了什么**：阶梯档位原来是 N 行「起 / 止 / 奖励」输入框。档位的**顺序关系、间距大小、
覆盖是否连续**这三件事全靠心算——结果是重叠没人发现（两个档位争抢同一笔订单），
断档没人发现（某个金额区间一分钱优惠都没有，而运营以为配全了）。尺上一眼可见。

**人话预览**是本屏成败的分水岭：schema 驱动的动态表单极易退化成一排看不懂的 key-value，
运营填完不知道自己配出了什么，于是要么不敢上线、要么上线后才发现配错。
实时翻译成「订单满 300 元减 50 元；订单满 600 元减 120 元。取最高档，不与其它满减叠加。」
是让运营敢按下发布的唯一手段。

#### 与规范的一处有意偏离

规范里的演示是「拖第 2 个卡子到 280 → 出现重叠斜纹 +『280–300 区间有 2 个档位争抢』」。
这要求编辑模型**允许拖出非法状态**。我改成**边界卡子**——每个卡子是相邻两档的公共边界，
拖动同时改左档上界与右档下界，**结构上产生不了重叠与断档**。

理由：让运营先拖出错误、再靠红色提示去修，是把校验当交互用；**能从源头杜绝的错误不该留给校验**。
校验没有删——它仍然跑，用来兜住**从库里读进来的**历史数据（那些可能本来就有重叠或断档）。

#### 区间语义的对齐

`[min, max)` 下界闭、上界开，与后端 `BenefitEvaluator.tierOf` 一致。
所以「上一档 max == 下一档 min」是**恰好衔接，不是重叠也不是断档**——这条最容易写反，单测专门钉了它。

#### 落地中修掉的两个阻断项（都不是 UI 问题）

**① `GET /list` 会把同一活动返回成多行。** P0-4 之后编辑已上线活动会保留线上 v1 另建草稿 v2
（`ActivityMarketingService:139-145`），而 `list()` 是 `findByIsDelOrderByModifiedStimeDesc` 无归并。
旧 `ListView` 直接 `v-for` 这批行，于是 **Vue `:key` 与 `data-testid="activity-row-{id}"` 同时重复**，
跨页选择还会把一个活动数成两个。修法是按 activityId 归并，主版本取**正在服务的那一版**
（`benchModel.mergeRows`）。

**② 批量下线会打到草稿，线上版继续发钱。** `bulkChangeStatus` 调的是 `changeStatus(id, null, target)`，
`version=null` → 取最高未删除版本 = 草稿 v2。于是「批量下线 23 个」把 23 个草稿置成下线、
**正在发钱的线上版一个都没停**，而回执还报 23 个全部成功——正是这个功能本来要消灭的那类静默失败。

先写测试把它钉成红的：

```
BulkStatusTest.bulkOfflineHitsTheServingVersionNotTheDraft
  批量下线后不得再有 ONLINE 版本 ==> expected: <true> but was: <false>
```

（同一用例的第一条断言 `rows.size()==2` 通过，顺带坐实了 ①。）

修法是把契约从裸 id 列表改成 `items:[{activityId, version}]`，由调用方按它在列表里看到的那一行传版本：
**下线传当前 ONLINE 版本，发布传要发的草稿版本**（`versionForTarget`）。
`version` 仍允许为 null（「随便哪一版」），但工作台不这么用——并且补了一条**反向验证**用例
`nullVersionHitsTheDraftInstead` 钉住「传 null 就会打到草稿」，防止哪天有人图省事改回去。

> 这是本 PR 唯一的后端改动。不改的话，前端无论怎么写都只能交付一个「点了像成功、实际没停」的批量按钮。

### PR-6 屏 2 玩法模板 — 完成

**起因是一句话反馈：「活动类型还是太少了」。** 查证后发现这句话对，但原因跟直觉不一样——

后端 `ActivityType` 有 5 个枚举位，`field-dict` 也把 5 个全返回了，可**实际能用的只有 2 个**：
前端 `enabledTypes` 过滤掉 `code !== 1 && code !== 5`，后端 `create` 也只放行这两个，
枚举 javadoc 自己写着「COUPONS / CPS / RIGHT_COUPON 保留枚举位但不实现链路」。

而卡在 2 个的根因是**权益按类型硬编码**（前端 `v-if activityType===1 / ===5` 两套表单，
后端按类型分支），这正是重构决策记录里写的「加一个玩法 = 五处齐动」。

**但这里有个被忽略的事实**：现有 2 个类型配上 6 个可用条件字段
（订单金额 / 购买数量 / 用户地域 / 用户标签 / 商品 SPU / 店铺），**本来就能表达 8 种玩法**，
只是没有名字——运营看到的是「活动类型：红包」，看不出自己能配出「满 300 减 50」还是「新客专享立减」。

所以本 PR 选的是**零后端改动**的那条路：给已有能力起名字并给出起点，而不是动权益模型。

#### 目录（12 张卡，8 可用 4 不可用）

| 组 | 玩法 | 怎么表达的 |
|---|---|---|
| 满减 | 无门槛立减 / 满 X 减 Y / 阶梯满减 / 满 N 件立减 | 红包 · 固定或阶梯金额（+ orderAmount / quantity 条件） |
| 定向 | 人群定向券 / 门店定向 / 地域定向 | 红包 · 固定金额 + userTags / storeId / userDistrictId 条件 |
| 赠品 | 满额赠品 | 买赠 + orderAmount 条件 |
| **不可用** | 折扣券 / 第二件半价 / 秒杀一口价 / 加价购 | 标灰并写明缺什么，见下 |

不可用的四个，每个都写清缺口而不是「敬请期待」：

- **折扣券** —— 权益形态只有固定/阶梯**金额**，没有百分比。规则表虽有 `redPackageAmountUnit`，
  但它全链路只被搬运、不参与任何计算，配成「折」也还是按元减。
- **第二件半价** —— 决策入口 `SpuDiscountRequest` 只有 `spuIdList / orderAmount / quantity`，
  **没有逐行单价**，算不出「第二件」是哪件、值多少。要行项模型，是入口契约的破坏性升级。
- **秒杀一口价** —— 现有形态都是「减多少」，没有「卖多少」；且秒杀要靠库存扣减防超发，
  而 `inventory` 是声明式、决策不读取。
- **加价购** —— 需要两阶段决策，当前链路一次性返回最终优惠。

#### 与规范的两处偏离

| # | 规范 | 实际 | 理由 |
|---|---|---|---|
| 1 | 「定向券包」列为**不可用**（「只有枚举位」） | 列为**可用** | 规范把它对应到未实现的 `RIGHT_COUPON(4)` 枚举。但作为玩法，「定向券」= 红包 + `userTags contains` 条件，今天就能配，且已用 e2e 验过预填能落进表单。把能做的说成不能做，和把不能做的说成能做一样有害 |
| 2 | 「件数折扣」一张卡 | 拆成两张 | 「满 N 件**减固定金额**」可用（quantity 是条件字段），「第 N 件 **M 折**」不可用（没有百分比形态）。合成一张会让运营以为打折能配 |

#### 顺带抓到的第三个装饰字段

编辑器的「发放方式」下拉一直提供**随机金额**，但 `redPackageTakeType` 全链路零计算读取——
`BenefitEvaluator.computeAmounts` 只是把 `redPackageAmount` 抄给 `computedAmount`，从不看它。
**配了随机，线上照样发固定值。** 与 `inventory`、`redPackageAmountUnit` 同族。
按库存红线 B 的先例处理：选项**保留但禁用** + 写明「决策链路不读取该字段」——
删掉会让人以为从来没有过这个能力，禁用才说明「有这个字段但没实现」。
