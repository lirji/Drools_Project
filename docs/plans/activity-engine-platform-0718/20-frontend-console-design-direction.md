## 0. 摘要（TL;DR）

- 现有活动前端是**挂在 Drools 演示台里的一个报表式子应用**（`activity.js`，纯原生 JS，`window.ActivityApp.mount(panel)`），4 个视图：列表 / 表单 / 详情 / 验证。**token 复用彻底、明暗主题自动跟随**，这是可以继承的最大资产。
- 但要撑起「决策中台 + 运营控制台」，现有前端缺**三根支柱**：① 没有独立的顶层导航与工作台首页；② 生命周期只有「上线/下线」二态，没有草稿→审核→灰度→回滚的可视化；③ 完全没有监控与效果分析界面。
- 本文给出：**7 项顶层 IA + 页面层级树**、**4 个高难界面的布局方向（ASCII 线框）**、**在现有 token 之上的设计系统基线（含 8 个生命周期状态色映射）**、**技术取向建议（分阶段：先不引框架，把渲染层做扎实；图表阶段再局部引依赖）**、以及**假设与待澄清**。

## 1. 现有前端审计（诚实评估）

### 1.1 信息架构现状

现有活动前端的实际形态（读 `app.js` `renderNav` 的 `g.external` 分支 + `activity.js`）：

- 整个活动模块是 Drools 演示台侧栏里的**一个导航项**：「工作台 · 列表/新建/验证」，点击把 `#panel` 交给 `activity.js` 接管。它**寄生**在 18 个 Step demo 的展示框架里，没有自己的产品级外壳。
- 进入后是**顶部子标签**（`.act-tabs`）：`活动列表` / `新建活动` / `优惠验证` 三个 tab；`详情` 不是 tab，靠列表行「详情」按钮进入（`state.route = "detail"`）。
- 表单是**单页长表单 + 右侧 sticky 提交栏**（`.demo-grid` 两栏，右栏 `.act-rail`），六个分区（基础信息 / 红包或买赠 / 商品绑定 / 资格条件树 / 合并策略 / 提交）全部常驻展开。
- 列表是 CSS grid 伪表格（`.alist-row`），6 列，行内 3 个操作按钮（详情 / 编辑 / 上线或下线）。

这套 IA 对「单人、单活动、报表式录入」够用，但它是**工具页**，不是**运营控制台**。

### 1.2 复用了哪些 token（可继承的资产清单）

`activity.css` 头注释明确写着"纯新增选择器，全部复用 styles.css 的 `--` token，删掉即可完全回退"。核对结果：**100% token 化**，无一处硬编码颜色/圆角/字体。已在用的 token：

| 类别 | 复用的 token |
| --- | --- |
| 表面/边框 | `--bg` `--bg-elev` `--bg-soft` `--border` `--border-strong` |
| 文字 | `--text` `--text-soft` `--text-faint` |
| 主色 | `--accent` `--accent-2` `--accent-soft` |
| 语义色 | `--ok/--ok-soft` `--warn` `--err/--err-soft` `--blue/--blue-soft` `--green/--green-soft` `--gold/--gold-soft` `--red/--red-soft` |
| 形状/字体 | `--radius`(14) `--radius-sm`(9) `--mono` `--sans` `--shadow` `--shadow-sm` |

明暗主题的落地方式也已成熟：`styles.css` 用 `@media (prefers-color-scheme: dark)` 给默认信号，再用 `:root[data-theme="dark"]` / `:root[data-theme="light"]` 让顶栏切换按钮的 `data-theme` 双向覆盖（`app.js initTheme` 写 `localStorage` + `document.documentElement.setAttribute`）。**控制台必须继承这套双主题机制，不能另起炉灶。**

现有可直接复用的组件类（值钱的部分）：`.sum-card / .kv / .col / .col-label`（卡片与键值）、`.status-pill .status-ok|error|pending`（状态胶囊）、`.tag .tag-blue|green|gold|red`、`.pill .pill-yes|no`、`.timeline .tl-row`（时间线雏形，监控/审计可复用）、`.chip`（分段/示例选择）、`.run-btn`（主按钮）、`.err-card`（错误卡）、`.price-row`（原价→现价，验证结果可复用）、`.dmn-grid / .dmn-cell`（三格指标，KPI tile 的雏形）。

### 1.3 生产控制台视角下的差距（按优先级分级）

诚实清点。**P0 = 阻断生产**、**P1 = 严重体验缺口**、**P2 = 打磨项**。

**P0（撑不起控制台的结构性缺失）**

1. **无独立顶层导航 / 无工作台首页**：运营进来第一屏应是「今天要处理什么」（待审核、待上线、即将过期、编译失败告警、核心指标），现在只有一个"列表"。
2. **生命周期只有二态**：`listRow` 里状态渲染是 `a.activityStatus === 1 ? pill-yes : pill-no`，`changeStatus` 只在 1/2 间切。后端也只有 0待上线/1上线/2下线。MVP 要求的**草稿 → 审核 → 发布 → 灰度 → 上线 → 下线 → 回滚**七态与**版本历史时间线**在前端**完全没有承载**。
3. **无监控 / 效果分析**：命中率、优惠金额、回退次数、决策延迟、编译失败——**一张图都没有**。这是 MVP 能力 4 的全部缺口。
4. **无审核 / 灰度界面**：`/status` 是自助上下线，没有"提交审核 → 审核人通过 → 灰度放量 → 全量"的流程界面，也没有版本 diff 对比。

**P1（严重体验缺口）**

5. **条件树构建器可用性偏原始**（详见 §3.1）：校验只有一个全局「预览（试编译）」按钮走服务端 `POST /preview`，**错误不定位到具体节点**；字段/运算符是裸 `<select>`（白名单一大就不可用）；值控件对枚举/布尔/日期字段一律退化成文本框（`LIST` 是逗号分隔字符串）；深层嵌套只有左边框缩进，**复杂条件不可读**，没有"人类可读回显"（如「订单金额 ≥ 100 且 用户标签 含 vip」）。
6. **列表无筛选/搜索/排序/分页**：`renderList` 一把梭 `GET /list` 全量。运营按状态、类型、业务线筛选是刚需。
7. **错误反馈不统一**：多数走 token 化的 `.err-card`，但 `changeStatus` / `loadForEdit` 失败用了原生 `alert()`（`activity.js:160,186`）——刺眼、不跟主题、不可访问。缺全局 toast / 通知机制。
8. **决策验证只给"赢家"**：`renderValidate` 只展示命中的那一个活动 + `traces` 字符串数组，**看不到"评估了哪些活动、为什么没命中"**，也没有决策版本号 / 结构化 trace / 可复现（replay）。

**P2（打磨项）**

9. 表单是长滚动，无草稿自动保存、无分步向导、无"未保存"离开拦截。
10. 条件树 `reTree()` 在改字段/运算符时**整树重建**（`activity.js:383`），大树会丢焦点/丢滚动位置。
11. 可访问性零散：删除按钮有 `aria-label`，但条件树里字段/运算符 `<select>` 无 label；异步状态无 `aria-live` 播报；焦点样式靠继承。
12. 移动端只考虑了表单单列 + 行横向滚动（`@media max-width:980px`），sandbox / 看板未做响应式。

**结论**：现有前端是**优秀的设计语言底座 + 单页工具**，不是控制台。演进策略应是**保留 token 与组件语汇，重建外壳（顶层 IA + 工作台）、补齐生命周期/审核/灰度/监控四大界面、把条件树与列表升级到生产可用**。

## 2. 控制台信息架构（IA）

### 2.1 顶层导航（推荐 7 项）

控制台应有**自己的产品外壳**（左侧主导航），而不是继续做 Drools 演示台里的一个条目。四类界面（配置 / 生命周期 / 验证 / 监控）映射到导航如下：

| # | 导航项 | 承载 | 对应 MVP 能力 |
| --- | --- | --- | --- |
| 1 | **工作台** Workbench | 首页：核心 KPI 概览 + 待办（待审核/待上线/即将过期）+ 告警（编译失败/回退激增）+ 最近活动 | 4（概览入口） |
| 2 | **活动管理** Activities | 列表（状态/类型/业务线筛选 + 搜索）→ 编辑器 / 详情 / 生命周期 | 1 配置 |
| 3 | **审核与发布** Review & Release | 审核队列、版本 diff、发布/灰度/回滚控制台 | 3 版本·审核·灰度·回滚 |
| 4 | **决策验证** Sandbox | 填上下文 → 调决策 API → 可视化命中/优惠明细/trace/决策版本 | 2 决策 + 护栏 |
| 5 | **效果监控** Monitoring | 命中率 / 优惠金额 / 回退 / 延迟 / 编译失败 图表看板 | 4 可观测·效果 |
| 6 | **接入与 API**（预留） | API Key、`field-dict` 字段字典参考、端点文档、接入示例 | 2 API 接入 |
| 7 | **设置**（预留） | 业务线管理、默认合并策略、角色/权限（未来）| — |

导航项 2–5 是 MVP 主战场；1 是入口聚合；6–7 标注为**预留**（占位，避免后期重排导航）。

### 2.3 与现有 Drools 演示台的挂载关系（务实建议）

现有活动子应用通过 `renderNav` 的 `g.external` 分支挂载，改动面极小、可数据级回滚（删 external group 即消失）——这是 `FRONTEND_PLAN.md` 采纳的 Option C。**控制台演进不必立刻推翻它**：

- **短期**：控制台仍作为演示台里的"外部子应用"存在，但把 `activity.js` 内部的**顶部三 tab** 升级为**左侧二级导航（§2.1 的 7 项）**，先在 `#panel` 内部长出控制台外壳。
- **中期**：当控制台自成体系（监控/审核/灰度都进来），再评估是否给它一个**独立入口页**（`/console`），与 Step 1–18 演示台并列，而不是嵌在其侧栏项里。
- 这条路径尊重 CLAUDE.md「没需求不提前加」与 FRONTEND_PLAN 的隔离原则：**外壳先在子应用内部演进，宿主框架尽量不动**。

## 3. 关键界面的设计方向（ASCII 线框 + 交互要点）

> 线框只表意布局与信息层级；所有色彩/间距/圆角落地时走 §4 的 token。

### 3.1 可视化规则 / 条件树构建器（升级现有雏形 → 生产可用）

现有 `renderTree/renderGroup/renderLeaf/valueControl` 已能拼 AND/OR 嵌套 + 白名单字段/运算符 + `RANGE/LIST/SCALAR` 值控件 + `POST /preview` 试编译。**升级重点是可读性、就地校验、错误定位、类型感知值控件、人类可读回显**。

```
┌─ ③ 资格条件（白名单条件树）───────────────────────────── [人读] [JSON] [DRL] ┐
│  空条件树 = 所有用户恒通过。字段/运算符仅从后端白名单选，服务端翻译成受控 Drools。 │
│                                                                              │
│  ┌ 组 ▸ 满足【全部 AND ▾】以下 ─────────────────  [+ 条件] [+ 子组] [⋯] ⊟折叠 ┐ │
│  │                                                                          │ │
│  │   ● 订单金额        [ ≥  ▾ ]   [ 100        ] 元                    [✕]  │ │
│  │                                                                          │ │
│  │   ● 用户标签        [ 包含任一▾]  [ vip ✕ ][ new ✕ ][+ 添加… ]        [✕]  │ │
│  │        ⚠ 值不能为空 — 至少选一个标签                                       │ │
│  │                                                                          │ │
│  │   ┌ 子组 ▸ 满足【任一 OR ▾】───────────────────  [+ 条件] [🗑 删组] ⊟ ┐   │ │
│  │   │   ● 用户地域    [ 属于 ▾ ]   [ 110000 ][ 310000 ]              [✕] │   │ │
│  │   │   ● 注册天数    [ 介于 ▾ ]   [ 0 ] ~ [ 30 ]                    [✕] │   │ │
│  │   └──────────────────────────────────────────────────────────────────┘   │ │
│  │                                              嵌套深度 3/5                 │ │
│  └──────────────────────────────────────────────────────────────────────────┘ │
│                                                                              │
│  实时预览： ✓ 编译通过 · 命中约束 3 项            〔自动，输入停止 500ms 后〕     │
│  ┌ 人类可读 ────────────────────────────────────────────────────────────────┐ │
│  │ 订单金额 ≥ 100 元  且  用户标签 含 (vip 或 new)  且                        │ │
│  │ ( 用户地域 ∈ {110000, 310000}  或  注册天数 在 0~30 之间 )                 │ │
│  └──────────────────────────────────────────────────────────────────────────┘ │
│  ▸ 展开查看翻译后的 Drools 约束 (DRL)                                          │
└──────────────────────────────────────────────────────────────────────────────┘
```

交互要点：

- **三视图切换**（右上 `[人读] [JSON] [DRL]`）：默认「人读」（把树渲染成中文自然语言，运营可读）；「JSON」给技术核对；「DRL」显示 `POST /preview` 返回的 `drl`。人读回显是现有完全缺失、又最提升可用性的一环。
- **就地校验 + 错误定位**：每个叶子在 blur/change 时做**客户端预校验**（对齐 `FRONTEND_PLAN` 边界：`between` 恰 2 值、`in/containsAny` 非空列表、`scalar` 单值、NUMBER 必须数值非空），错误就地显示在该行下方（`.field-error` 已有），并给该控件加 `.field-invalid` 红框；**顶部预览汇总"N 处待修正"并可点击跳到首个错误节点**。保留 `POST /preview` 作为提交前的服务端权威门（它跑真 translator + 编译）。
- **值控件按字段类型切换**（升级现有 SCALAR/RANGE/LIST）：
  - `NUMBER` → 数字输入（带单位后缀，如"元/天"）；`RANGE` → 双数字输入。
  - `ENUM`（如地域、类目、标签）→ **可搜索多选 chip**（不是逗号分隔字符串），值来自 `field-dict` 该字段的候选。
  - `BOOLEAN` → 分段开关（复用 `segToggle`）。
  - `DATE` → `datetime-local`。
- **字段/运算符可搜索**：白名单一大，裸 `<select>` 不可用 → 升级为**带搜索的下拉**（typeahead 过滤 `field-dict.fields`）；选字段后按 `field.operators` 白名单重填运算符（现有已有联动逻辑，保留）。
- **可读性**：每个组显示 `满足【全部/任一】` 的自然语言头 + **可折叠**（⊟）+ 深度指示 `3/5`；子组用左侧强调边框（`--accent-soft`，现有 `.ctree-children` 已是）+ 轻微背景分层（`--bg-soft`）。
- **性能/焦点**：改字段/运算符**只重渲染受影响节点**，不整树重建（修 §1.3 P2-10 丢焦点问题）；值输入沿用 `oninput` 就地改 state 不重渲染。
- **预览自动化**：输入停止 500ms（防抖）自动触发预览，替代手点按钮；`preview` 恒 200 读 `ok`。

### 4.5 空态与加载态

统一规范（现有零散，需成体系）：

- **加载态**：列表/看板用**骨架屏**（`--bg-soft` 占位块 + 微光），而非纯文字"加载中…"（现有 `renderList` 用文字）；按钮内联加载沿用 `.run-btn:disabled`（现有）；`field-dict` 加载中时下拉禁用走 `node.disabled=true`（**注意 `el()` 对 `{disabled:false}` 也会 setAttribute，见 FRONTEND_PLAN 修正 8**）。
- **空态**：三类——① 首次无数据（列表：`.row-empty` "暂无活动 + 新建 CTA"，现有已有雏形）；② 筛选无结果（"无匹配 + 清除筛选"）；③ 看板时间范围无数据（居中提示 + 放宽范围建议）。空态**必带下一步 CTA**，不留死胡同。
- **异步状态播报**：状态区加 `aria-live="polite"`（现有 `.status-line` 只是视觉），让读屏用户感知"提交中/成功/失败"。

### 4.6 错误与校验反馈规范

分三层，与现有能力对齐并补齐：

1. **就地字段校验**（表单/条件树）：`.field-error`（红字，现有）+ `.field-invalid`（红框，现有）+ `aria-invalid="true"` + `aria-describedby` 指向错误文案；条件树顶部汇总"N 处待修正 → 跳转首个错误"。
2. **卡片级错误**（请求失败）：`.err-card`（现有），带 HTTP 状态 + 可读 hint（现有 `renderError` 的 hintMap：400 规则/参数、404 不存在、409 冲突）；**DRL 编译错含行号**（后端 400 带行号，Sandbox/预览要透传显示）。
3. **全局通知 Toast**（替换 `alert()`）：上下线/发布/回滚等一次性操作结果用 token 化 toast（成功 `--ok`、失败 `--err`、警告 `--gold`），4s 自动消失 + 可手动关闭，`role="status"`。

校验时机：条件树 blur 就地校验 → 提交前 `POST /preview` 服务端权威门 → 提交失败卡片级 + toast。**preview 恒 200 读 `ok` 字段**（现有约定，保留）。

### 4.7 light/dark 双主题与可访问性（具体做法）

**双主题**（继承现有机制，勿另造）：

- 一切颜色**只用 `--` token**，禁止硬编码 hex（现有 `activity.css` 已 100% 遵守，控制台延续）。新组件的 dark 表现**自动由 token 承接**——因为 token 在 `@media (prefers-color-scheme: dark)` 与 `:root[data-theme]` 双向定义。
- **图表是唯一例外**：SVG/canvas 里的类别色需**显式读 dark 版 token**（`getComputedStyle` 取 `--accent` 等），并在 `data-theme` 切换时重绘；深色色阶是 token 里**另选**的值，不是浅色翻转（§3.4）。
- 顶栏主题按钮沿用 `app.js initTheme` 的 `data-theme` + `localStorage` 逻辑，控制台不重复实现。

**可访问性**（WCAG AA 目标，逐条给做法）：

- **对比度**：正文/背景 ≥ 4.5:1，大字/图形 ≥ 3:1。现有 `--text` on `--bg-elev`、`--text-soft` 需在**两个主题都**抽样验证；状态徽章的"前景 token on 背景 token"组合逐一过一遍（尤其 dark 下 `--gold`/`--accent-2` 软背景）。构建时用对比度检查器核对，本文标注为**待验证项**。
- **颜色不单独承载信息**：状态/图表 identity 一律**色 + 文字 + 形状/图标**三重编码（§4.1、§3.4）；delta 用 ▲▼ 而非仅红绿；命中/淘汰用 ✓/✕ + 文字。
- **键盘可达**：所有交互（tab 切换、条件树增删、下拉、模态、抽屉）可 Tab 到达 + Enter/Space 激活 + Esc 关闭浮层；焦点顺序符合视觉顺序；**焦点样式**沿用 `:focus` 的 `box-shadow: 0 0 0 3px accent-soft`（现有 `.pp-input:focus` 已有），确保每个可聚焦元素都有可见焦点环。
- **触控目标**：交互元素 ≥ 44px（现有小按钮 `.row-del/.ctree-mini` padding 偏小，移动端需增大命中区）。
- **语义与读屏**：表单控件都有关联 `<label>`（现有 `labeled()` 已做，但条件树 select 缺 label → 补 `aria-label`）；异步区 `aria-live`；模态 `role="dialog" aria-modal="true"` + 焦点陷阱；表格用真 `role` 或语义结构（现有 grid 伪表需补 `role="table/row/cell"` 或改真 `<table>`）。
- **减弱动效**：`@media (prefers-reduced-motion: reduce)` 下关闭 sparkline/过渡动画（现有 `.run-btn` 有 transform 动效，需尊重该偏好）。
- **文字缩放**：布局用相对单位 + flex/grid，支持浏览器文字放大到 200% 不破版（现有 px 字号偏多，控制台关键容器改用 rem/相对布局）。

## 5. 技术取向建议（原生 JS vs 轻量框架）

**背景**：现有是零依赖原生 JS（IIFE + `el()` hyperscript + 手动整块重渲染），CLAUDE.md 与 FRONTEND_PLAN 都明确"不引入前端框架/构建工具/CDN"。这是**要尊重的强约束**。

**诚实评估**：控制台复杂度相对报表页是**量级上升**——多路由、抽屉/模态、筛选、版本 diff、图表、更多且更耦合的状态。现有 `el()` + 全子树重建的模式会撞到三堵墙：① **丢焦点/丢滚动**（改一个字段整树重建，§1.3 P2-10 已现苗头，条件树/大表更严重）；② **性能**（大列表/深树每次全量 rebuild）；③ **状态弥散**（无集中 store，跨视图状态难维护）。纯字符串式 DOM 重建**撑不到**监控 + 审核 + 灰度全进来。

**推荐：分阶段，先"把原生做扎实"，把"引框架"这颗子弹留到确有必要处。**

| 方案 | 取向 | 权衡 |
| --- | --- | --- |
| A. 纯原生现状不变 | 保持 `el()` 全重建 | 零依赖✓ 与现有一致✓ ／ 焦点丢失、性能、状态弥散 ✗✗ —— **判定：撑不住** |
| **B. 原生 + 轻量渲染纪律（推荐）** | 加**集中 store + keyed 列表 diff + 组件化模块拆分**（仍无构建、无框架） | 零依赖✓ 尊重 CLAUDE.md✓ 修掉焦点/性能✓ ／ 需自律、要写少量基础设施 |
| C. no-build 响应式库 | 同源自托管一个**免构建** ESM 小库（如 Preact+htm ~11KB / 或 petite-vue），`<script type=module>` 直引 | 真正的响应式/组件化✓ 无构建步骤✓ ／ 引入一个依赖（与 CLAUDE.md "不引框架" 有张力，需团队拍板） |
| D. 完整框架 + 构建 | React/Vue + Vite | 生态最全 ／ **违背"无构建/无框架"约束**，本项目定位（学习脚手架）不划算 —— 判定：否 |

**一句话结论**：**先走 B —— 保持零依赖原生，但把渲染层升级（集中 store + keyed diff + 模块化），足够撑起配置/生命周期/审核/Sandbox 四类界面**；**唯一值得单独破例的是图表**——建议在监控阶段"手绘 SVG"或**局部自托管一个免构建微型图表文件**，而不是为了画图把整个框架拉进来。**只有当团队确认要在全站做重交互时，才把 C（免构建响应式库）作为下一步升级**，且必须与 CLAUDE.md 的"无框架"约束显式对齐后再定。**最终技术选型由 frontend-plan / 架构评审拍板，本节仅为设计侧建议。**

## 6. 假设与待澄清

### 【假设】（基于现有代码与文档的合理推断，落地前需确认）

- **[假设] 生命周期七态是目标设计**：现有后端仅 `activity_status` 0待上线/1上线/2下线，`/status` 只在其间切；**草稿/审核中/已通过/灰度中/已回滚 + 版本历史/回滚**均无对应端点。§3.2 的看板是**目标态蓝图**，多数状态需新增后端支持。
- **[假设] 版本历史可列举**：`create` 已是 version+1 语义（编辑生成新版本），假设后端能**列出某活动所有版本并激活指定版本**（当前 `/status` 只切当前版本，无"激活旧版本"能力）。
- **[假设] 灰度语义**：假设灰度为"按比例放量 / 或用户白名单"，命中键类似 Step 14 canary（AgendaFilter 放行）/ Step 16 KieScanner（绑 ReleaseId 热替换）的模型 —— 复用项目已有的护栏/灰度心智。
- **[假设] 监控数据源**：假设可从 Micrometer/Prometheus（Step 15 已接）派生"命中率/优惠额/回退/延迟/编译失败"，或后端另给聚合分析端点。
- **[假设] 业务线为小预设集**（mall / smoke 等固定值），沿用 FRONTEND_PLAN 的假设，便于筛选与策略解析。
- **[假设] Chinese-first**、单运营视角为主；审核流暗示至少"编辑 / 审核"两种角色，但 MVP 鉴权是非目标（FRONTEND_PLAN）。
- **[假设] 决策 API 可返回评估全景**：§3.3 的"所有候选 + 淘汰原因 + 决策版本"假设决策端点能给出（现有 `DiscountView` 只给赢家 + trace 字符串）。

### 【待澄清问题】（需求缺失，不臆造，交付前确认）

1. **审核/发布流程是否本期落地？** 是否存在与"编辑者"分离的"审核者"角色？发布必须审核通过，还是自助？后端目前无审核端点——这块进不进 MVP？（直接决定 §3.3 审核与 §2.1 导航项 3 的实现深度）
2. **灰度（canary）的确切语义？** 按百分比放量 / 用户白名单 / 业务线维度 / 按活动版本？命中键是什么（userId 哈希 / 标签 / 地域）？（决定 §3.2 灰度控件与 §3.1 编辑器⑤的字段）
3. **版本回滚是否支持、粒度如何？** 后端能否列出历史版本并"激活指定旧版本"？回滚是新建一个 version 还是切指针？（决定 §3.2 版本时间线的操作能力）
4. **监控数据源与口径？** 有没有活动级/业务线级的分析 API（命中率、优惠总额、回退率、延迟分位、编译失败）？时间粒度与留存多久？（决定 §3.4 能画到多细）
5. **决策 API 能否返回"完整评估集 + 决策版本"？** 还是只有赢家？（决定 §3.3 评估全景能否实现，这是 Sandbox 最大增量）
6. **规模预期？** 活动数量级、条件树白名单字段数量级？（决定列表是否要服务端分页/搜索、条件树字段选择是否必须 typeahead）
7. **控制台是单业务线还是多业务线/多渠道？** （影响导航是否需要业务线切换器与全局筛选）
8. **保留的 COUPONS/CPS/RIGHT_COUPON 三类活动类型是否要在本期实现？**（当前后端 400、前端禁用；决定编辑器②优惠规则区的可扩展性设计）
