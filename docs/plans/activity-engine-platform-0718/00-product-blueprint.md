# 活动引擎平台 · 产品蓝图（Product Blueprint）

**版本**：v1.0 · Draft
**作者**：Alex（产品经理）
**最后更新**：2026-07-18
**面向读者**：架构 Agent、前端 Agent、后续实施同学
**上游依据**：`docs/activity-marketing.md`、`docs/plans/activity-marketing-port-0712-1917/{FINAL_PLAN,IMPLEMENTATION_PROGRESS}.md`、`CLAUDE.md`、`com.lrj.drools.activity` 现有代码

> **本文的定位**：把现有「活动营销」学习脚手架（`com.lrj.drools.activity`）演进成一个**生产级「活动引擎平台」**的产品蓝图。首个接入场景是电商活动接入。
> **用户已拍板的前提**（不再讨论，直接作为约束）：
> 1. 平台形态 = **决策中台 + 运营控制台**（对外实时决策 API + 内部运营配置控制台）。
> 2. **单租户为主**，多租户 SaaS 放二期。
> 3. **MVP 四项能力全进**：①可视化配置控制台 ②实时决策 API + 引擎护栏 ③版本化·审核·灰度·回滚 ④可观测 + 效果分析。
>
> **标注约定**：全文用 `【已具备】`（现有代码已实现，直接复用）/ `【要新建】`（生产平台新增）/ `【要接入】`（本仓库已有能力，但尚未接入活动决策路径，需打通）三种标记，避免架构/前端误判工作量。

## 1. 平台定位与价值主张

**一句话定位**：
> 活动引擎平台是电商的「营销决策中台」——运营在控制台自助把「什么人、买什么、满多少、给多少优惠 / 送什么赠品」配成可审核、可灰度、可回滚的规则，电商系统只需**一次 API 接入**，就能在下单结算时实时拿到「命中哪些活动、优惠多少、赠品是什么」。

**它为电商解决什么**：

| 痛点（现状：每个活动写死代码） | 平台带来的改变 |
| ---- | ---- |
| 每上一个红包 / 满减 / 买赠都要研发改代码、发版、回归 | 运营在控制台自助配置，规则即数据，**研发零改动**接入一次即可复用所有后续活动 |
| 活动逻辑散落在订单 / 结算 / 商品各处，口径不一致 | 优惠决策**收敛到一个引擎**，一处配置、一处生效、一处观测 |
| 活动上线全靠人肉核对，错了直接影响真金白银 | **提交审核 → 灰度放量 → 全量**的受控发布链路，错了**一键回滚**止血 |
| 活动上了不知道效果，复盘靠导数据拉表 | 决策日志 + 效果看板，**命中率 / 优惠 / 延迟**实时可见 |
| 活动逻辑写飞了（死循环 / 超时）拖垮下单主链路 | 引擎护栏（最大规则数 / 超时 / fail-safe 回退），**活动故障不阻塞交易** |

**核心价值主张（一句话给三类人）**：
- 给**运营**：不写代码，当天就能把一个活动配好、审好、灰度上线。
- 给**研发/接入方**：接一次决策 API，之后所有活动无感复用，且活动挂了不拖垮下单。
- 给**业务负责人**：每个活动都能看到命中率与效果，发布可控、回滚可控、风险可控。

## 2. 目标用户 / 角色与权限

单租户内按**角色**（RBAC）划分职责，不做租户隔离（多租户放二期）。

| 角色 | 核心任务 | 控制台触点 | API 触点 | 权限边界 |
| ---- | ---- | ---- | ---- | ---- |
| **运营（Operator）** | 建活动、配规则/商品池/资格条件、提交审核、发起灰度/回滚、看效果 | 活动工作台（列表/报表式表单/条件树构建器/商品池圈选/预览/效果看板） | 只读 `/field-dict`（渲染下拉） | 只能配**白名单字段**拼条件，**永不写 DRL**；不能自审自发（若职责分离开启） |
| **审核（Reviewer）** | 发布把关：看版本 diff + 生成的规则约束，通过 / 驳回（带意见）、决定灰度放量节奏 | 审核队列、活动 diff 视图、灰度放量控制 | — | 只能审核不能改配置；通过才能进入可发布态 |
| **研发 / 接入方（Integrator）** | 在下单/结算调用决策 API 拿优惠、监控 API 健康、读字段字典对齐契约 | 只读：API 文档、字段字典、决策 API 健康面板 | **写**：`/decision/evaluate`（或现有 `/spu-discount`+`/gifts`）；读 `/field-dict` | 只消费决策结果，不碰活动配置与审核 |
| **平台管理员（Admin）** | 管字段白名单/合并策略默认值、开关与灰度比例、护栏阈值、角色授权 | 平台管理区（字段字典/策略/开关/护栏/权限） | 全部 | 平台级配置，影响所有活动 |
| （次要）**业务负责人 / 观察者（Viewer）** | 只读看板：活动效果、灰度对比 | 只读效果看板 | — | 纯只读 |

> 现状对齐：来源项目**未迁移鉴权**（`docs/activity-marketing.md` 明确「鉴权」在未迁移清单）。因此 **RBAC 与角色体系整体是 `【要新建】`**。现有 REST 端点全部无鉴权，生产版需在网关/服务层补角色校验。

## 3. 活动品类地图（分期）

### 3.1 现有已支持（`【已具备】`，代码已跑通）

| 能力 | 现状 | 代码落点 |
| ---- | ---- | ---- |
| **红包 RED_PACKAGE(1)** | 固定金额 / 随机金额（`DistributionMode`）+ 阶梯满减（`LADDER`，`redPackageRangeAmount` JSON 分档） | `ActivityType`、`ActivityQueryService#spuDiscount` |
| **买赠 BUY_AND_GET(5)** | 赠品保留/汇总（`GIFT` 场景），赠品明细结构化落 `activity_gift` | `ActivityQueryService#buyAndGetGifts` |
| **多活动折扣合并** | MAX / MUTEX / STACK / PRIORITY 四策略（`StackStrategy`），业务线级兜底策略 | `StackStrategy`、`saveStrategyIfPresent` |
| **资格淘汰 ELIGIBILITY** | 可视化条件树 → 受控 Drools 约束（`not ActivityRuleContext(...)` fail-closed），字段/运算符白名单 | `RuleConditionTranslator`、`RuleField`、`RuleOperator` |
| **商品池自动圈选** | 规则驱动圈选 `demo_product`，diff 幂等物化进绑定表（`bind_source=AUTO`） | `ActivityPoolMatchService` |
| **枚举位保留未实现** | COUPONS(2) / CPS(3) / RIGHT_COUPON(4)：后端 400 拒、前端禁用 | `ActivityType`、`validateCommon` |

### 3.2 首期（MVP）做哪些 —— **产品化已有两类活动，不新增活动类型**

> **PM 取舍（这是关键判断，请架构/前端注意）**：MVP **不新增任何活动类型**，聚焦把已跑通的**红包（含阶梯）+ 买赠 + 资格淘汰 + 折扣合并 + 商品池圈选**这套能力**产品化到生产级**（四项平台能力）。
>
> **为什么这样切**：
> - 用户拍板的 MVP 核心是「**四项平台能力全进**」，不是「铺更多玩法」。把控制台/决策API护栏/审核灰度回滚/可观测这条**发布与运营主干**打磨扎实，比多上三五个活动类型价值高得多。
> - 现有红包+买赠已经能覆盖一个完整的电商接入场景（资格判定 + 优惠计算 + 赠品），足以验证端到端接入旅程。
> - 每多一个活动类型都会拉长审核/灰度/效果分析的验证面。先用两类活动把「一条鱼吃干净」，再横向扩品类，风险最低。

MVP 品类范围：

| 活动品类 | MVP 是否做 | 说明 |
| ---- | ---- | ---- |
| 红包（固定 / 随机 / 阶梯满减） | ✅ 做 | 产品化：接入护栏、审核、灰度、回滚、效果分析 |
| 买赠 | ✅ 做 | 同上 |
| 折扣合并策略（MAX/MUTEX/STACK/PRIORITY） | ✅ 做 | 作为红包/买赠的跨活动合并能力，非独立品类 |
| 资格淘汰 + 商品池圈选 | ✅ 做 | 作为上述活动的配置能力 |
| 满减券 COUPONS | ❌ 不做（→ v2 首选） | 见下 |
| 秒杀 / 拼团 / 砍价 / 抽奖 / 积分 / CPS | ❌ 不做（→ v3） | 见下 |

### 3.3 二期（v2）做哪些 + 取舍理由

参考来源「未迁移」清单（`FINAL_PLAN.md`「来源存在但本次不迁移」），结合电商实际频次给出**我的优先级判断**：

| 品类 | 优先级 | 取舍理由 |
| ---- | ---- | ---- |
| **满减券 COUPONS(2)** | **v2 首选** | 电商**最高频**促销玩法；枚举位已留；可**大量复用**现有 LADDER（满减分档）+ DISCOUNT（合并）基建，边际成本最低 |
| **会员日 / 会员专享** | v2 | 几乎零新建：直接复用**资格淘汰 `userTags` / `userDistrictId`** 白名单字段即可表达「会员/等级/地域专享」，属于「配置能力 → 产品化包装」 |
| **A/B 效果对比 / 预算软控** | v2 | 让灰度从「小流量验证」升级为「命中 vs 对照的效果度量」；预算软控给红包/买赠加发放上限（**软控，不做强一致扣减**，见 Non-goal） |

### 3.4 三期（v3）做哪些 + 取舍理由

| 品类 | 取舍理由 / 边界 |
| ---- | ---- |
| **秒杀** | 强库存扣减 + 高并发写，与「决策中台只判资格与优惠、**不做真实库存扣减**」的定位**有张力**。若做，必须明确边界：**平台只判「是否有秒杀资格 / 秒杀价」，库存扣减仍在电商侧**。放 v3 是因为它逼平台碰 Non-goal 的库存一致性。 |
| **拼团 / 砍价 / 门店拼团** | 依赖**订单状态机 + 社交裂变 + 履约**，超出「实时无状态决策」范畴，需引入有状态流程编排，重，放 v3。 |
| **积分 / 权益券 RIGHT_COUPON(4)** | 依赖积分账户 / 权益系统对接，平台只能返回「应发什么」，发放与核销是另一套系统，放 v3 与权益系统一并规划。 |
| **CPS 订单分润(3)** | 依赖订单成交回传 + 分润结算，是「事后结算」而非「事中决策」，与决策中台不是同一形态，放 v3。 |
| **多租户 SaaS + 计费** | 用户已明确放二期之后；涉及租户隔离 / 计量计费 / 数据面隔离，独立大工程。 |

## 4. 活动全生命周期

### 4.1 状态机（生产版）

```
  ┌─────────┐  提交审核   ┌──────────────┐  通过   ┌───────────┐  发布(灰度)  ┌──────────┐  全量   ┌─────────┐
  │  草稿    │ ─────────▶ │  待审核       │ ─────▶ │  审核通过  │ ─────────▶ │  灰度中   │ ─────▶ │  已上线  │
  │ DRAFT   │            │PENDING_REVIEW│        │ APPROVED  │            │ CANARY   │        │ ONLINE  │
  └─────────┘ ◀───────── └──────────────┘        └───────────┘            └──────────┘        └─────────┘
       ▲         驳回          │  驳回(带意见)                                   │ 灰度不达标           │  到期/手动
       │  编辑(version+1)       ▼                                              ▼ 回滚                 ▼  下线
       └───────────────── ┌───────────┐                                  ┌──────────┐          ┌─────────┐
                          │  已驳回    │ ──编辑──▶ 回 DRAFT                 │ 回滚      │          │ 已下线   │
                          │ REJECTED  │                                  │ ROLLBACK │          │ OFFLINE │
                          └───────────┘                                  └──────────┘          └─────────┘
```

### 4.2 各状态的进入/退出条件、操作人、版本演进

| 状态 | 进入条件 | 谁操作 | 退出去向 | 版本演进 |
| ---- | ---- | ---- | ---- | ---- |
| **草稿 DRAFT** `【要新建】` | 新建 / 编辑保存 / 被驳回后再编辑 | 运营 | 提交审核 | 编辑即 `version+1`，旧版本 `isDel=1`（`【已具备】`并发保护 409） |
| **待审核 PENDING_REVIEW** `【要新建】` | 运营提交 | 系统 | 审核通过 / 驳回 | 冻结当前版本，审核期间不可再编辑（编辑需先撤回） |
| **审核通过 APPROVED** `【要新建】` | 审核人通过 | 审核 | 发布进入灰度 | 记录审核人 + 时间 + 意见 |
| **已驳回 REJECTED** `【要新建】` | 审核人驳回 | 审核 | 运营编辑 → 回 DRAFT | 保留驳回意见，编辑触发 `version+1` |
| **灰度中 CANARY** `【要新建】` | 审核通过后发布 | 审核 / 运营 | 全量上线 / 回滚 | 决策 API 按灰度维度命中该版本 |
| **已上线 ONLINE** `【已具备】(status=1)` | 灰度达标全量 / 直接全量 | 审核 / 运营 | 下线 / 回滚 | 决策 `filterBeginActivities` 取「已上线 + 时间范围内」（`【已具备】`） |
| **已下线 OFFLINE** `【已具备】(status=2)` | 到期 / 手动下线 | 运营 | 终态（可复制新建） | 现有：已下线活动不可编辑（`【已具备】`校验） |
| **回滚 ROLLBACK** `【要新建】` | 灰度/全量异常止血 | 运营 / 审核 | 切回上一 ONLINE 版本 或 直接 OFFLINE | 复用版本化：指向历史稳定 `version` |

### 4.3 复用现有基座（务必复用，别重写）

- **版本化**：`【已具备】` 编辑 = 带 `activityId` 的 create，旧版本逻辑删除、新版本 `version+1`（`ActivityMarketingService#create`）。
- **幂等**：`【已具备】` 同 `requestId` 重复提交返回首次结果。
- **并发冲突 409**：`【已具备】` `softDeleteVersion` 影响行数为 0 → `IllegalStateException` → 409。
- **状态机约束**：`【要新建】` —— ⚠️ **现有 `changeStatus` 不限制状态转换（任意 → 任意）**，仅 setStatus。生产版必须替换为**受控状态机**（校验合法转换 + 记录操作人/时间/意见），并新增 DRAFT / PENDING_REVIEW / APPROVED / REJECTED / CANARY / ROLLBACK 这些**现有枚举没有的状态**（现有仅 NORMAL/ONLINE/OFFLINE/PENDING_EFFECT）。

## 5. MVP 范围与验收标准

四项能力拆成用户故事（As a … I want … so that …）+ 验收标准。`[x]` 已具备可直接复用，`[ ]` 需建/接入。

### 能力① 可视化配置控制台

**US-1 报表式建活动**
> As a 运营, I want 用报表式表单（基础信息 / 红包或买赠规则 / 商品绑定 / 资格条件树 / 合并策略）创建活动, so that 不写代码就能上活动。
- [x] 复用 `/create`、`/field-dict`、现有 `activity.js` 报表式表单 + 递归条件树构建器（`【已具备】`）
- [ ] 前端所有下拉的**唯一数据源是 `/field-dict`**（禁止硬编码枚举，防漂移）
- [ ] 活动类型只启用红包(1)/买赠(5)，其余禁用并给出「二期支持」提示

**US-2 保存前预览校验**
> As a 运营, I want 在保存前预览资格条件是否合法, so that 不用等上线才发现规则写错。
- [x] 复用 `/preview`（恒 200，返回 `ok` + 生成的约束 + DRL）（`【已具备】`）
- [x] 非白名单字段 / 非法运算符被拒并给出可读原因（`RuleConditionTranslator`）（`【已具备】`）

**US-3 商品池圈选自动绑定**
> As a 运营, I want 圈选商品池自动绑定商品, so that 不用手工逐个绑 SPU。
- [x] 复用 `poolRefs` + `bind_source=AUTO` + diff 幂等刷新，返回 `autoBoundCount`（`【已具备】`）

**US-4 活动列表与详情**
> As a 运营, I want 看到活动列表和详情（规则/条件/绑定/买赠/池）, so that 管理在办活动。
- [x] 复用 `/list`、`/{id}`（`【已具备】`）
- [ ] 详情增加**版本 diff 视图**（供审核用，见 US-10）

### 能力② 实时决策 API + 引擎护栏

**US-5 结算调决策 API 拿优惠**
> As a 电商系统, I want 在结算时调决策 API 传订单上下文, so that 拿到命中活动+优惠金额+赠品+trace。
- [x] 复用 `/spu-discount`（资格→阶梯→折扣合并 + trace + mode）、`/gifts`（买赠）（`【已具备】`）
- [ ] MVP **建议聚合**成统一入口 `/decision/evaluate`（一次拿红包+买赠所有命中），减少接入方多次调用（`【要新建】`，见待澄清 #3）

**US-6 引擎故障 fail-safe 不阻塞下单**
> As a 接入方, I want 规则异常/超时时回退不阻塞下单, so that 活动系统故障不拖垮交易主链路。
- [x] 复用 fail-safe：引擎异常/空决策 → legacy 旧逻辑（取最大红包）+ `mode=legacy`（`【已具备】`）
- [x] 全局开关 `activity.marketing.rule-engine.enabled` 一键切 legacy（`【已具备】`）

**US-7 引擎护栏防跑飞**
> As a 平台管理员, I want 给决策引擎加护栏（最大规则数/执行超时/AgendaFilter）, so that 规则写错不会跑飞拖垮延迟。
- [ ] **接入本仓库 Step 14 能力**（`fireAllRules(max)` / `halt()` / `AgendaFilter`）到活动决策路径（`【要接入】`）
- [ ] 超阈值熔断 + 记录 + 告警

**US-8 决策 API 低延迟高可用**
> As a 接入方, I want 决策 API 稳定低延迟（P99 < 目标值）且高可用, so that 能嵌入结算主链路。
- [x] 复用 StatelessKieSession（线程安全可缓存）+ KieBase 内容级缓存（`【已具备】`，`ActivityRuleRuntimeService`）
- [ ] 压测达标（P99 目标见待澄清 #3）+ 可用性 SLO

### 能力③ 版本化·审核·灰度·回滚

**US-9 提交审核后才能上线**
> As a 运营, I want 把活动提交审核由审核人把关后才能上线, so that 防止错误活动直接上线。

### 5.1 Non-goals（本期明确不做）

| 不做的事 | 原因 / 边界 |
| ---- | ---- |

| 复杂履约（赠品发货 / 权益到账） | 只返回「应发赠品清单」，履约由电商/权益系统对接 |

| QLExpress | 坚持纯 Drools（`CLAUDE.md` 项目定位） |

## 9. 假设与待澄清

> 严格区分：`【假设】`=为推进而做的合理默认（若用户不反对即作为工作前提）；`【待澄清】`=需用户拍板、会实质影响架构/前端设计的问题。**缺失需求不臆造成事实。**

### 9.1 【假设】（为推进采用的默认，欢迎纠正）

1. 单租户，RBAC 在租户内按角色划分，不做租户级数据隔离。
2. 决策 API 同步嵌入结算/购物车主链路，因此 **fail-safe 回退默认常开**，活动引擎故障绝不阻塞下单。
3. 库存字段（`inventory`/`userInventory`）MVP 只做**配置与展示**，**不做强一致扣减**（扣减在电商侧）。
4. 现有 `version+1` / `requestId` 幂等 / 409 并发冲突直接复用为生产版本化基座，不重写。
5. 现有全局 `rule-engine.enabled` 是「引擎级」回退开关，**不等于**「按活动/按流量」灰度；灰度放量为新建能力。
6. 现有 `changeStatus` 无状态机约束（任意→任意），生产版替换为受控状态机 + 新增审核相关状态。
7. 活动品类 MVP 不新增，先把红包/买赠产品化到生产级。
8. 效果分析的「核销/GMV」类指标依赖电商回传事件，平台自身只掌握「决策命中」数据。
9. 引擎护栏（Step 14）与指标（Step 15）在本仓库已存在，MVP 走「接入活动决策路径」而非从零实现。

### 9.2 【待澄清】（需用户拍板，按影响面排序）

1. **审核工作流形态**：单级审核还是多级（如运营主管 + 风控）？驳回后是否必须回 DRAFT 重走全流程？是否强制**职责分离**（运营不能自审自发）？→ 影响状态机与 RBAC。
2. **灰度放量维度**：按 `userId` 哈希百分比？按地域/门店？按用户标签 cohort？是否需要**A/B 对照组**（命中 vs 不命中）来度量效果？→ 影响决策 API 命中逻辑与效果看板。
3. **决策 API 契约与延迟预算**：是否要聚合入口 `/decision/evaluate`（一次拿所有命中）还是保留 `/spu-discount`+`/gifts`？调用方是否同步阻塞在结算链路？可接受的 **P99 延迟预算**具体是多少（决定护栏超时阈值与容量规划）？
4. **效果核销数据来源**：平台只知「决策命中」，「优惠核销率 / GMV 提升」需电商**回传订单/核销事件**——是否要求接入方回传？核销口径（下单即核销 vs 支付成功核销）？→ 决定效果分析能做到哪一层。
5. **库存/预算控制边界**：红包/买赠是否需要平台侧做**发放上限**（`inventory` 扣减 / 预算封顶）？若需要，是**强一致**（DB 行锁，来源有 `lock(id,quantity)`）还是**软控**（允许少量超发）？→ 直接决定是否触碰 Non-goal 的库存扣减，是最大的边界问题。
6. （次要）**回滚语义**：回滚是「切回上一个 ONLINE 版本」还是「直接下线」？是否需要保留**完整版本历史可浏览**（来源未迁移「版本历史浏览/回滚」）？
7. （次要）**权限粒度**：运营权限是否需要按**业务线 `bizLine` / 活动类型**再切分？
8. （次要）**决策日志留存与回放**：留存多久？是否需要单条决策**可回放**（输入上下文 + 命中 trace）用于对账/客诉排查？
```
