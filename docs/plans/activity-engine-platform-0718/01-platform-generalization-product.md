## 0. 一图看懂这次升级改了什么

| 维度 | 原电商蓝图（`00-product-blueprint`） | 本次升级 |
| ---- | ---- | ---- |
| 服务对象 | 单租户、电商一条线 | **多租户 SaaS**，任意业务线（电商 + 出行 + 未来 N 条） |
| 上下文字段 | **编译期固定**（`ActivityRuleContext` 的 Java getter + `RuleField` 枚举白名单） | **运行时注册的元数据**（每业务线自助注册 schema，字段即数据） |
| 接入新业务线 | 改平台代码（加 fact 字段 / 改枚举 / 改翻译器） | **零平台代码**：注册 schema + 选类型 + 配合并策略即可 |
| 活动类型 | 红包 / 买赠（电商语义硬编码） | **可扩展 benefit-type 注册表**（红包 / 买赠 / 多单奖励 / 阶梯奖励 …），红包与阶梯的机制被证明业务线无关 |
| 权益 | 订单折扣 / 赠品 | 抽象权益：折扣 / 赠品 / **现金奖励到账**（平台只判「应发什么」，履约在 caller 侧） |

| 发布/审核/灰度机器 | 为电商设计 | **原样复用**（业务线无关），仅在 key 上加租户维度 |

**一句话**：把「一个电商的营销决策中台」升级为「**任何行业都能自助接入的营销决策 SaaS**」——同一套 artifact / 审核 / 灰度 / 护栏机器，靠一层**元数据 schema** 和一层**租户隔离**，同时服务电商的「满 100 减 20」和出行的「窗口内跑满 20 单奖 30 元」。

## 1. 重定位

### 1.1 一句话新定位

> **活动引擎平台是「多租户 · 元数据驱动的营销活动决策 SaaS」**——任何业务线（电商、出行、金融、本地生活……）**只需在控制台注册自己的上下文 schema、选启用的活动/权益类型、配一套合并策略，零平台代码就能配活动、接一个决策 API**，在自己的业务热路径实时拿到「命中哪些活动、发多少权益、发什么权益」；发布受审核/灰度/回滚管控，引擎故障 fail-safe 降级绝不阻塞业务主链路。

### 1.2 它对「任意业务线」解决什么

原蓝图讲的是「电商不用为每个红包改代码」。升级后这句话对**所有行业**成立，且多了一层「平台方不用为每个新客户/新行业改代码」：

| 主体 | 痛点 | 平台带来的改变 |
| ---- | ---- | ---- |
| **接入方（任意业务线）** | 促销/激励逻辑写死在业务代码里，换个行业、换个玩法都要重写 | 上下文字段、活动类型、合并策略全是**自助注册的配置**；一次接决策 API，之后所有活动无感复用 |
| **平台方（SaaS 运营）** | 每来一个新行业客户就要平台工程介入加字段、加类型、改翻译器 | 新行业接入退化为**运营/客户自助注册**；平台工程只在「注册一种全新权益类型」这种真·扩展点介入（见 §6） |
| **业务负责人（跨行业通用）** | 活动效果不可见、发布不可控、故障拖垮主链路 | 命中率/权益额/延迟实时可见；审核→灰度→全量→一键回滚；护栏 + fail-safe 隔离故障 |

### 1.3 和原电商蓝图的边界差异（哪些变、哪些不变）

**变（本文新增/改造的）**：
1. **元数据层**：上下文字段从「编译期 Java fact」变为「运行时注册的 schema」（§3、§7.3-1 是最大改造点）。
2. **租户层**：新增 tenant 作为最高隔离/配额/计费边界（§2）。
3. **类型注册表**：活动/权益从「电商两类硬编码」变为「可注册可扩展的 benefit-type 目录」（§6）。
4. **第二业务线**：出行（司机激励）作为通用性验证，端到端跑通（§3.4、§6.3）。
5. **角色**：新增平台管理员 / 租户管理员，原角色降为租户内作用域（§4）。

**不变（原蓝图 + 后端 FINAL_PLAN 已定，本文照单复用，不重新设计）**：
- **发布与治理机器**：artifact（不可变内容制品）/ manifest（发布单）/ pointer（CAS 版本指针）/ outbox / audit / 审核状态机 / 多级签署 / 多维灰度 / A/B / 回滚 —— 这些**天然业务线无关**，只是发布单里装的内容不同。本文只要求它们的 **key 增加租户维度**（`release_key = tenantId:bizLine`），协议不动。
- **引擎护栏**（Step 14 stateful `fireAllRules(max)`/`halt()`/`AgendaFilter`）、**指标**（Step 15 低基数 tag）、**fail-safe 降级**（D1：`NO_PROMOTION`）、**版本化基座**（`version+1`/`requestId` 幂等/409 CAS）。
- **安全红线**：运营永不写 DRL，只拼白名单条件树 → 受控翻译（`RuleConditionTranslator` fail-closed）。**这条在元数据化后不仅不退让，反而要更强**（白名单从闭合枚举变成动态数据，滥用面变大，见 §7.3-2）。
- **已定决策 D1 / D2 继续生效**：D1 `NO_PROMOTION` 降级 + 库存/预算仅展示不扣减；D2 多级审核 + 强制职责分离 + 多维灰度 + A/B。对出行同样适用（现金奖励的 `NO_PROMOTION` = 引擎故障时不发奖，防超发，财务安全）。

## 2. 对象层级：租户 → 业务线 → 活动 → 版本

### 2.1 四层模型与各层的隔离/配置边界

```
Tenant（租户）  —— 外部客户 / 计费与隔离边界
  │  隔离：数据物理/逻辑隔离、API Key 归属、配额、用量计量、计费
  │  配置：租户级开关、护栏默认阈值、成员与角色、订阅套餐
  │
  └─▶ BizLine（业务线）  —— 建模 / schema 边界（一个租户可有多条）
        │  隔离：schema 命名空间、启用的活动/权益类型、合并策略默认值
        │  配置：★上下文 schema（字段+类型+运算符+候选值）★ ← 元数据核心
        │        启用的 activityType 白名单、benefit-type 白名单、默认合并策略
        │  发布 key：release_key = tenantId:bizLine（灰度/pointer 以此为粒度）
        │
        └─▶ Activity（活动）  —— 一个具体活动
              │  作用域：绑定在某 bizLine 的 schema 上，条件只能用该 schema 注册过的字段
              │  生命周期：DRAFT→PENDING_REVIEW→APPROVED→CANARY→ONLINE→OFFLINE（+REJECTED/ROLLBACK）
              │
              └─▶ Version（版本）  —— 不可变版本 = artifact 单元
                    编辑即 version+1，旧版本逻辑删；发布物指向具体 activityId+version 的不可变 artifact
```

### 2.2 逐层职责与边界表

| 层级 | 是什么 | 隔离边界 | 配置边界 | 落到哪 |
| ---- | ---- | ---- | ---- | ---- |
| **租户 Tenant** `【要新建】` | SaaS 的一个外部客户（一家公司/一个签约主体） | **数据隔离**（每表带 `tenant_id`，查询强制租户过滤）；API Key 归属租户；**配额**（QPS/活动数）；**用量计量 + 计费** | 租户级护栏默认值、成员/角色、订阅套餐、开关 | 新 `activity_tenant` 表 + 所有业务表加 `tenant_id` 列 |
| **业务线 BizLine** `【要改造】` | 租户内的一个建模域（mall / ride / …） | **schema 命名空间隔离**（mall 的 `orderAmount` 与 ride 的 `completedTrips` 各自成套，互不可见）；`release_key` 粒度 | ★**上下文 schema**★、启用的活动/权益类型白名单、默认合并策略 | 现 `bizLine` 已是字符串字段，`【要新建】` `activity_bizline` + `activity_context_schema`（字段字典表，替代 `RuleField` 枚举） |
| **活动 Activity** `【已具备】+【要改造】` | 一个具体活动配置 | 只能用**所属 bizLine 已注册**的字段拼条件（翻译器按注册 schema 校验，非按枚举） | 类型/规则/条件树/绑定/合并策略 | 现 `activity_manage` 等表 + 加 `tenant_id`/`biz_line` |
| **版本 Version** `【已具备】` | 不可变版本 = 制品单元 | `version+1`；发布物指向 `activityId+version` | —（版本内容冻结） | 现 `version+1`/409 基座 + 后端 `activity_rule_artifact` |

### 2.3 厘清 multi-tenant 与 multi-business-line 的关系（关键概念，勿混）

这是最容易被误解的地方，明确写清：

| | **多租户（multi-tenant）** | **多业务线（multi-business-line）** |
| ---- | ---- | ---- |
| **本质** | **隔离/商业**维度：外部客户之间的数据隔离、配额、计费边界 | **建模/schema**维度：同一租户内不同领域的上下文语义 |
| **谁定义** | 平台方（SaaS 运营）签约/开通 | 租户管理员自助注册 |
| **答什么问题** | 「这条数据/这次调用属于哪个付费客户」 | 「这次决策用哪套字段语义（电商的还是出行的）」 |
| **关系** | **1 : N**——一个租户下可挂多条业务线（如一个集团同时有 mall + ride，共享配额/计费，但两套 schema 完全隔离）；也可以一个租户只有一条业务线 |
| **踩坑提醒** | 两个**不同租户**各自都有一条叫 `mall` 的业务线，是**完全隔离**的两套数据与 schema，不能因为同名就串 |

**产品判断**：schema/类型/合并策略这些「怎么建模」的能力挂在 **bizLine** 层；隔离/配额/计费这些「谁在用、用了多少、怎么收钱」挂在 **tenant** 层。**不要**把 bizLine 当租户用（会丢掉「一个集团客户多条线共享账单」的能力），也**不要**把 tenant 当 bizLine 用（会把商业隔离和建模语义耦死）。

## 3. 自助接入旅程（核心）

> 这是本次升级的**心脏**。「元数据驱动·全自助·零平台代码」这句口号，成立与否全看这条旅程能不能真的走通。下面用**电商 vs 出行两条真实 schema 并列**，证明同一套注册机制能表达两者。

### 3.1 端到端流程（新租户/新业务线从零接入）

```
① 开通租户（平台侧）
   平台管理员开通 Tenant → 生成租户空间 + 首个「租户管理员」账号
   （MVP：平台管理员开通；全自助注册-signup = 二期，见 §9）
        │
        ▼
② 注册业务线（租户侧，租户管理员）
   在租户内建 BizLine（如 "ride"）→ 得到一个 schema 命名空间
        │
        ▼
③ ★定义上下文 schema★（零平台代码的关键一步）
   逐字段声明：字段 key + 类型（NUMBER/STRING/ENUM/ARRAY/BOOLEAN）
              + 允许的运算符 + （ENUM/字典型）候选值列表
   例：ride 注册 completedTrips(NUMBER)、driverLevel(ENUM: L1..L5)、timeSlot(ENUM: peak/off-peak)…
   保存即写入 activity_context_schema（数据，不是代码）；
   翻译器 / field-dict / 前端下拉从此以该 schema 为唯一数据源
        │
        ▼
④ 选启用的活动类型 + 权益类型
   从平台「类型注册表」（§6）勾选本业务线要用的：
   电商→ 红包(DISCOUNT)/买赠(GIFT)；出行→ 多单奖励(CASH_REWARD 固定)/阶梯奖励(CASH_REWARD ladder)
   （勾选 = 零代码；若要一种注册表里没有的全新权益类型 → 平台工程注册一次，见 §6.2）
        │
        ▼
⑤ 配合并策略
   选该业务线默认合并策略：MAX/MUTEX/STACK/PRIORITY（§复用 StackStrategy）
   例：电商同 SPU 多红包取 MAX；出行多单+阶梯同时命中可配 STACK 累加或 MAX 取大
        │
        ▼
⑥ 建活动（租户内运营）
   报表式表单选类型 → 配规则（阶梯档位阈值字段 = 本 schema 里的某 NUMBER 字段）
   → 拖资格条件树（字段只能选本 schema 注册过的）→ 预览校验 → 保存草稿 version+1
   → 提交审核 → 灰度 → 全量（复用原生命周期与治理机器）
        │
        ▼
⑦ 拿决策 API 凭证接入（租户内研发）
   领取本租户的 API Key（scope 到 tenant/bizLine）→ 在自己业务热路径调
   POST /decision/v1/evaluate { tenantId?, bizLine, context:{...本 schema 字段...}, requestId }
   → 拿 { hitActivities[], benefits[], degraded, decisionVersion, trace }
```

**「零平台代码」的准确边界（诚实，不夸大）**：
- **零代码成立于**：开通租户、注册业务线、定义 schema（从平台支持的字段类型里选）、选启用的已注册类型、配合并策略、建活动、接决策 API。**这覆盖了 99% 的日常接入**。
- **零代码不成立于**：①新增一种**平台注册表里没有的全新权益类型**（如「抽奖」，需要新的计算/载荷/履约语义）；②新增一种**全新字段值类型**（如 GEO 地理围栏）或**新运算符语义**。这两类是平台的**真·扩展点**，由平台管理员/工程「注册一次，全租户可用」（§6.2）。**把这条说清楚，胜过承诺一个做不到的「万能自助」。**

### 3.2 电商 vs 出行 —— 同一套机制的两条 schema 并列

**电商（mall，消费者侧）上下文 schema**：

| 字段 key | 标签 | 类型 | 允许运算符 | 候选值 | 现状 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| `orderAmount` | 订单金额 | NUMBER | gt/ge/lt/le/eq/between | — | `【已具备】` |
| `quantity` | 购买数量 | NUMBER | gt/ge/lt/le/eq/between | — | `【已具备】` |
| `spuId` | 商品 SPU | NUMBER | eq/in | — | `【已具备】` |
| `storeId` | 店铺 | NUMBER | eq/in | — | `【已具备】` |
| `userDistrictId` | 用户地域 | STRING | eq/in/notIn | （地域字典，可选） | `【已具备】` |
| `userTags` | 用户标签 | ARRAY | contains/notContains/containsAny | （标签字典，可选） | `【已具备】` |

启用类型：红包（DISCOUNT）、买赠（GIFT）｜合并：MAX/MUTEX/STACK/PRIORITY｜决策：结算时**同步单次**｜权益：订单折扣 / 赠品。

**出行（ride，司机侧激励，类滴滴）上下文 schema**：

| 字段 key | 标签 | 类型 | 允许运算符 | 候选值 | 现状 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| `driverId` | 司机 ID | STRING | eq | — | `【要新建】`（注册即得） |
| `cityId` | 城市 | STRING | eq/in | （城市字典，可选） | `【要新建】` |
| `driverLevel` | 司机等级 | **ENUM** | eq/in | **{L1,L2,L3,L4,L5}** | `【要新建】`+`【要改造】`（需 ENUM 类型，见 §7.3-1） |
| `completedTrips` | 窗口内完单数 | NUMBER | gt/ge/between | —（**caller 预聚合传入**） | `【要新建】` |
| `onlineHours` | 在线时长 | NUMBER | gt/ge/between | — | `【要新建】` |
| `timeSlot` | 时段 | **ENUM** | eq/in | **{peak, off-peak}** | `【要新建】`+ENUM |
| `vehicleType` | 车型 | **ENUM** | eq/in | **{economy, comfort, xl}** | `【要新建】`+ENUM |

启用类型：多单奖励（CASH_REWARD 固定=资格+单阈值）、阶梯奖励（CASH_REWARD ladder，阈值字段 = `completedTrips`）｜合并：租户配（如 MAX 或 STACK）｜决策：**累积型**（司机端预聚合 `completedTrips` 传入，**平台无状态、只对 caller 提供的上下文决策**）｜权益：现金奖励发到司机账户。

**两条 schema 揭示的通用性证据（给架构 Agent 的核心论据）**：
1. **字段只是数据**：mall 的 `orderAmount` 和 ride 的 `completedTrips` 都是 `NUMBER` 字段配 `ge/between`，翻译器产出的约束形状完全一样（`(completedTrips >= 20)` vs `(orderAmount >= 100)`）。字段名/语义的差异**不进代码，只进 schema 数据**。
2. **阶梯机制业务线无关**：出行「阶梯奖励」= 现有 `LADDER` 场景，**唯一差别是阈值字段从 `orderAmount` 换成 `completedTrips`**。只要把「阶梯阈值字段」做成可配（当前 `LADDER` 隐含绑死 `orderAmount`，`【要改造】`），阶梯机制一行业务代码都不用改就服务了出行。
3. **多单奖励 = 资格门 + 固定权益**：出行「多单奖励（跑满 N 单奖固定额）」= 现有红包「资格淘汰（`completedTrips >= N`）+ 固定金额」的同构，只是权益从「订单折扣」换成「现金到账」。
4. **平台仍无状态**：出行是「累积型」，但**累积在 caller 侧完成**（司机端预聚合窗口内完单数再传入）。平台**不做窗口聚合、不引 CEP**，只对 caller 给的 `completedTrips` 做阈值决策——与现有「每请求 newSession + 只看入参上下文」模型**完全一致**，无需新增有状态能力。这一条极其重要：它意味着出行接入**不触碰**引擎的状态/时钟维度，风险面小。

**结论**：接入出行需要的**新代码**只有三样——①元数据 schema 层（让字段成为数据）②`ENUM` 值类型 + 候选值 ③`CASH_REWARD` 权益类型 + 阶梯阈值字段可配。**这三样恰好就是本次升级的通用抽象，不是为出行一次性打的补丁。** 出行是验证这三样通用性的「第二条鱼」。

### 3.3 决策 API 契约的通用化（在原契约上加什么）

原后端 `POST /decision/v1/evaluate` 请求形如 `{ userId, userTags[], userDistrictId, spuIdList[], orderAmount, quantity, bizLine, requestId }`——这是**电商字段硬编码在契约里**。通用化后：

- **请求**：`{ tenantId(或从 API Key 推导), bizLine, context: { <本 bizLine schema 注册的任意字段> }, requestId, options }`。`context` 从「固定字段列表」变为「**按 bizLine schema 校验的动态键值包**」。电商传 `context:{orderAmount, quantity, spuIdList, userTags...}`，出行传 `context:{driverId, cityId, driverLevel, completedTrips, timeSlot...}`。服务端按该 bizLine 注册的 schema 校验类型/必填。
- **响应**：`hitActivities[]` 不变；`discount{...}` 泛化为 `benefits[]`（每项带 `benefitType∈{DISCOUNT,GIFT,CASH_REWARD}` + 结构化 payload）；`degraded/degradeReason/decisionVersion/route/timings` 保持必返。
- `bizLine` 已是原契约必填字段（后端 §8.1），**升级点是把 tenant 维度补进 key、把 context 从固定字段改为 schema 校验的动态包**。

### 3.4 出行接入的一次完整走查（把旅程走实）

某出行公司（租户 `T-RIDE`）要上「工作日晚高峰跑满 20 单奖 30 元、25 单奖 45 元、30 单奖 70 元」：
1. 平台管理员开通租户 `T-RIDE` + 首个租户管理员。
2. 租户管理员注册业务线 `ride`，定义上述 ride schema（`completedTrips`/`driverLevel`/`timeSlot`/`cityId`…）。
3. 勾选启用「阶梯奖励（CASH_REWARD ladder）」，配默认合并策略 `MAX`。
4. 运营建活动：阶梯阈值字段选 `completedTrips`，分档 `[20,25)→30`、`[25,30)→45`、`[30,∞)→70`（复用 `redPackageRangeAmount` 的 JSON 分档结构，字段语义换掉）；资格条件树拖 `timeSlot == peak AND cityId in [北京,上海]`；预览校验（翻译器按 ride schema 通过）→ 保存 → 提交多级审核 → 5% 灰度（按 `driverId` 哈希分桶，复用 D2 多维灰度）→ 全量。
5. 司机端在司机完单后，聚合「本晚高峰窗口内完单数」= 22，调 `POST /decision/v1/evaluate {tenantId:T-RIDE, bizLine:ride, context:{driverId, cityId:北京, timeSlot:peak, completedTrips:22}}` → 返回 `benefits:[{benefitType:CASH_REWARD, amount:30, ...}]` + `decisionVersion`。
6. 出行系统把 30 元发到司机账户（**履约在 caller 侧**，平台只判「应发 30」）。引擎故障时返回 `degraded, NO_PROMOTION`（不发奖，防超发）。

全程**平台零代码**，只有 §7.3 的三样通用抽象是本次一次性投入。

## 4. 角色升级

在原有（运营 Operator / 审核 Reviewer / 研发 Integrator / 平台管理员 Admin / 观察者 Viewer）之上，**拆分出两级管理员**，并把原角色收敛为**租户作用域**。

| 角色 | 作用域 | 核心任务 | 权限边界 | 现状 |
| ---- | ---- | ---- | ---- | ---- |
| **平台管理员 Platform Admin** `【要新建】` | **跨租户**（SaaS 运营方） | 开通/停用租户；**注册表维护**（新 benefit-type / 新字段值类型 / 新运算符，见 §6.2）；平台级护栏默认；配额套餐模板；计费配置；平台可观测 | 能跨租户做**平台级**扩展与治理；**不**代替租户做日常活动配置（职责分离）；是唯一能「注册全新类型」的角色 | 原「Admin」升格为此 |
| **租户管理员 Tenant Admin** `【要新建】` | **单租户内** | 注册/配置本租户的**业务线 + 上下文 schema**；勾选启用的活动/权益类型；配默认合并策略；管理本租户成员与角色；管本租户 API Key；看本租户用量/配额 | **不能跨租户**；**不能注册全新类型**（那是平台级）；是「自助接入旅程」§3 步②③④⑤的主要操作者 | 全新 |
| **运营 Operator** `【已具备角色定义】` | **租户内**（可再按 bizLine 细分） | 建活动、配规则/条件树/商品或司机维度/合并、提交审核、看效果 | 只能配**本租户本 bizLine schema 白名单字段**，永不写 DRL；不能自审自发（D2 强制职责分离） | 原角色 + 加租户维度 |
| **审核 Reviewer** `【已具备角色定义】` | **租户内** | 多级签署审核（D2）、看 diff + 生成约束、控灰度放量 | 只审不改；多级链（初审→复审→终审）；租户隔离 | 原角色 + 加租户 + D2 多级 |
| **研发/接入方 Integrator** `【已具备角色定义】` | **租户内** | 调决策 API 拿权益、读本 bizLine schema 对齐契约、监控 API 健康 | 只消费决策结果；API Key scope 到本租户/bizLine；不碰配置与审核 | 原角色 + 加租户维度 |
| **观察者 Viewer** `【已具备角色定义】` | **租户内** | 只读效果/灰度看板 | 纯只读、租户隔离 | 原角色 + 加租户维度 |

**权限边界的两条硬规则**：
1. **租户是硬隔离墙**：除 Platform Admin 外，任何角色的任何操作/查询都**强制带 `tenant_id` 过滤**，越界即 403。这是 SaaS 的生命线，不可退让（§7.3-3）。
2. **「注册全新类型」是平台特权**：Tenant Admin 能自助做「用已有积木搭房子」（注册 schema、选类型、建活动），但「造一块新积木」（新 benefit-type / 新值类型）只有 Platform Admin 能做。这条边界保证平台的受控扩展与安全（新类型的计算/载荷/护栏语义必须经平台评审，不能让租户注入）。

> 现状对齐：原蓝图已注明 RBAC 整体 `【要新建】`（来源未迁移鉴权）。本次在其上再加**租户维度**与**两级管理员**。鉴权基础设施（控制台 SSO/JWT、决策 API Key）仍是待定的 D6，本文不重复决策，只声明角色模型。

## 6. 活动/权益类型注册表（产品视角）

### 6.1 从「硬编码两类」到「可扩展 benefit-type 注册表」

现状：`ActivityType` 是枚举（红包/买赠等 5 位，仅 2 位实现），权益语义（折扣/赠品）**硬编码在决策与结果模型里**。升级为**类型注册表**——把「活动类型」与「权益类型（benefit-type）」拆开、注册化：

- **活动类型（activityType）**：面向运营的「玩法」外壳（红包、买赠、多单奖励、阶梯奖励…）。
- **权益类型（benefit-type）**：面向计算与履约的「发什么」内核。一个 benefit-type 声明三件事：
  1. **计算策略**：固定 / 随机 / 阶梯（ladder，阈值字段可配）。
  2. **载荷 schema（payload）**：这类权益返回给 caller 的结构化字段（折扣→`finalAmount/strategy`；赠品→`giftName/giftNum/...`；现金→`amount/currency/account`）。
  3. **履约目标**：平台只返回「应发什么」，**履约在 caller 侧**（折扣→电商结算应用；赠品→电商履约；现金→出行发到司机账户）。

### 6.2 新类型如何「注册即用」（区分两种扩展）

| 扩展动作 | 谁做 | 是否零代码 | 说明 |
| ---- | ---- | ---- | ---- |
| **启用一个已注册类型** | 租户管理员 | **✅ 零代码** | 从注册表勾选（如 ride 勾选「阶梯奖励」），配阈值字段/档位/合并即用 |
| **注册一个全新 benefit-type** | 平台管理员/工程 | ❌ 需平台一次性工作 | 实现该类型的计算策略 + 载荷 schema + 决策/结果映射 + 护栏语义，注册进注册表；之后**全租户可勾选复用**（「注册一次，处处可用」） |

**这就是「可扩展」的准确含义**：日常接入（选已有类型）零代码；扩充平台能力边界（造新类型）由平台受控完成。**不夸大成「任何权益都能自助注册」**——新权益的计算与履约语义无法凭配置凭空生成。

### 6.3 跨业务线类型地图

| 活动类型 | benefit-type | 计算策略 | 阈值字段 | 电商 | 出行 | 现状 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| 红包 | DISCOUNT | 固定/随机/**ladder** | orderAmount | ✅ | — | `【已具备】` |
| 买赠 | GIFT | 命中即发（按规则） | — | ✅ | — | `【已具备】` |
| **多单奖励** | **CASH_REWARD** | **固定**（资格+单阈值） | completedTrips | — | ✅ | `【要新建】`（=资格门+固定，同构红包固定额） |
| **阶梯奖励** | **CASH_REWARD** | **ladder**（阈值字段可配） | completedTrips | — | ✅ | `【要改造】`（=LADDER，阈值字段换 orderAmount→completedTrips） |
| （二期）满减券 | DISCOUNT | ladder | orderAmount | v2 | — | 枚举位已留 |
| （二期）抽奖/积分/权益券 | 需新 benefit-type | — | — | v3 | v3 | 平台注册新类型 |

**地图揭示的产品判断**：MVP 只需 **3 个 benefit-type（DISCOUNT / GIFT / CASH_REWARD）** 就覆盖两条验证业务线的全部玩法。DISCOUNT/GIFT 已具备，CASH_REWARD 是唯一新增权益类型 + 阶梯阈值字段可配是唯一改造。**类型注册表的价值不在 MVP 铺量，而在把「加类型」从「改核心代码」降级为「注册表登记」**，让 v2/v3 的满减券/抽奖/积分能低成本接入。

## 7. 更新 MVP 范围与 Non-goals

### 7.1 MVP 做什么（多租户 + 元数据驱动下的最小可信闭环）

**MVP 目标一句话**：**跑通「通用抽象 + 电商 + 出行两条线」**——用两条真实业务线证明「元数据驱动 + 多租户」不是 PPT，是能端到端配活动、接决策 API、拿权益、可审核可灰度可回滚可观测的东西。

| 能力块 | MVP 内容 | 复用/新建 |
| ---- | ---- | ---- |
| **通用抽象（本次三大投入）** | ①元数据 schema 层（字段即数据、ENUM+候选值、翻译器按注册 schema 校验且仍 fail-closed）②benefit-type 注册表（DISCOUNT/GIFT/CASH_REWARD）+ 阶梯阈值字段可配 ③决策 API context 泛化（动态键值包按 schema 校验） | `【要改造】`+`【要新建】` |
| **租户层（最小）** | tenant 实体 + 全表 `tenant_id` + 查询强制租户过滤 + API Key scope 到租户 + **决策调用/活跃活动/编译数计量** + 每租户 QPS/活动数/schema 上限限额 + 租户用量看板 | `【要新建】`；rate_limit 字段已在 |
| **两条业务线端到端** | 电商（复用红包/买赠）+ 出行（多单奖励/阶梯奖励/现金权益）**都能配活动、接决策 API、拿权益、可观测** | 电商 `【已具备】`；出行 `【要新建】`（靠通用抽象，非专属代码） |
| **发布治理机器** | 审核状态机 + 多级签署（D2）+ 多维灰度 + A/B + 一键回滚 + artifact/manifest/pointer/outbox/audit + 护栏（Step14）+ fail-safe（NO_PROMOTION，D1）+ 指标（Step15） | **原样复用**，仅 key 加租户维度 |
| **自助接入旅程** | §3 的注册租户→注册 bizLine→定义 schema→选类型→配合并→建活动→拿凭证，控制台可走通 | `【要新建】` 控制台 + 复用后端配置/发布/决策端点 |

**MVP 的验收信号（Alex 的判定标准）**：一个**从没接触过电商**的出行团队，在**不改一行平台代码**的前提下，能自助注册 ride schema、配出「跑满 20 单奖 30 元」的阶梯奖励活动、接决策 API 拿到 `CASH_REWARD:30`、并在看板看到命中率与延迟——**这一刻，通用性被证明，MVP 达成**。

### 7.2 Non-goals（本期明确不做）

沿用原蓝图 Non-goals（真实支付、真实库存扣减、运营写 DRL、QLExpress、券码发放/核销、复杂履约…全部继续不做），**本次新增以下平台化 Non-goals**：

| 不做的事 | 原因 / 边界 | 去向 |
| ---- | ---- | ---- |
| **复杂计费出账 / 发票 / 对账 / 支付** | MVP 只计量+限额+看用量；出账是独立财务系统工程 | 二期 |
| **跨租户分析 / benchmark** | 涉及跨租户数据聚合与隐私边界，与租户硬隔离有张力 | 二期 |
| **租户全自助 signup / SCIM / 自助 SSO 接管** | MVP 由平台管理员开通租户；自助注册与身份联邦是独立工程 | 二期 |
| **租户自助注册全新 benefit-type / 值类型 / 运算符** | 新类型的计算/载荷/履约/护栏语义无法凭配置生成，必须平台受控扩展 | 平台特权（非租户自助），持续演进 |
| **平台侧做窗口聚合 / 有状态累积（CEP）** | 出行的「累积」在 caller 侧完成，平台保持无状态只对入参决策——**刻意不碰**，守住无状态定位与低风险 | 若未来真需平台侧聚合，另立大工程评估 |
| **第三条及以上业务线** | MVP 用电商+出行两条证明通用即可；更多线是通用性成立后的横向复制 | 通用性验证后按需 |
| **精细化数据驻留 / 分地域物理隔离** | MVP 逻辑隔离（tenant_id 过滤）足够；物理/地域隔离是合规驱动的重工程 | 二期（合规触发） |
| **现金权益的到账履约 / 资金流 / 幂等发放** | 平台只判「应发多少现金」，**发放与幂等在出行侧**（与电商折扣履约在电商侧同理） | caller 侧（永不进平台） |

### 7.3 ★诚实标注：这次范围跃迁的代价★

> 这是本文最该被决策者读的一节。原蓝图 MVP 是「单租户、电商一条线、把已有红包/买赠产品化」。本次跳到「多租户 + 元数据驱动 + 第二业务线」，**代价真实且不小**，逐条摊开：

**代价 1（最大）· 决策上下文从「编译期 Java fact」改为「运行时元数据」，动的是引擎心脏**
现状 `ActivityRuleContext` 是**固定 Java 类**（`getOrderAmount()`/`getUserTags()` 等硬 getter），`RuleField` 是**闭合枚举**，`RuleConditionTranslator` 产出的约束（如 `(orderAmount >= 100)`）**直接引用这些 getter**。要让字段变成「运行时注册的数据」，上下文 fact 必须从**类型化 getter** 改为**元数据/Map 承载的通用 fact**（如 `ContextFact` 持 `Map<String,Object>` + `number("completedTrips")`/`string("cityId")`/`hasTag(...)` 受控访问器），翻译器改为**按注册 schema 生成约束**。**这不是加个字段，是把决策路径与翻译器这两个最安全敏感、测试最重的组件重构**。→ 给架构 Agent：这是承重改造，必须在 M0 就把「Map 承载 fact」的接缝立住，**晚改 10 倍成本**。

**代价 2 · 安全白名单从「闭合枚举」变「动态数据」，滥用面变大，fail-closed 门槛更高**
枚举白名单是编译期闭合的、天然安全。改成每租户注册的 schema 后，「白名单」成了运行时数据——一个粗心/恶意租户可能注册**超大 schema、超深条件树、畸形候选值**拖垮翻译器/编译/内存。→ 必须新增**每租户的 schema 字段数上限、条件树节点/深度上限、候选值数量上限**（§5.2），并保证翻译器对**动态 schema 仍严格 fail-closed**（未注册字段/越权运算符/类型不符一律拒）。安全红线不退让，反而要加固。

**代价 3 · 全链路加租户维度，隔离/收敛/基数全面扩面**
每张表 + artifact/manifest/pointer/decision-log/effect-daily 都要加 `tenant_id`；`release_key` 从 `bizLine` 变 `tenantId:bizLine`；多实例 pointer 收敛、指标基数（tenant 作 tag 需像 bizLine 一样设白名单硬上限，超出归 `other`）、**跨租户隔离测试**全部扩面。任一处漏掉租户过滤 = 数据串租户 = SaaS 致命事故。

**代价 4 · 排期：建模面较原单租户电商 MVP 约翻倍**
如果排期固定，**必须有取舍**。Alex 的建议取舍（明确写出，供决策）：
- **不砍**「两条线通用性验证」——那是本次升级**唯一的意义**，砍了就退回改代码接业务线的老路。
- **砍/推**：①benefit-type 只做 3 个（DISCOUNT/GIFT/CASH_REWARD），②计费只做计量+限额、**出账全推二期**，③租户开通用平台管理员手动、**自助 signup 推二期**，④第三条线不做。
- **保持 M0 薄片不被撑大**：M0 仍是「单租户、单 bizLine=mall、单活动、stable pointer、护栏 + 决策 API 骨架」，**但从 M0 起就用 Map 承载 fact + 预留 tenant_id 列**（只是值先固定），避免 M2 接出行时回头重构心脏（呼应后端 §15「先切薄片」的落地建议）。

**一句话代价总结**：本次升级把「难度」从「把已有电商能力做扎实」变成「**先造一层通用抽象，再用两条线证明它**」——多出的是**元数据层 + 租户层**两层地基和**一次决策心脏重构**。这笔投入的回报是：此后接第 N 条业务线趋近零平台成本。**值不值，取决于是否真有多业务线/多租户的确定需求**——用户已拍板有，故建议投。

## 9. 假设与待澄清

> 严格区分：`【假设】`=为推进采用的合理默认（不反对即作工作前提）；`【待澄清】`=需用户拍板、会实质影响架构/前端的问题。**缺失需求绝不臆造。**

### 9.1 【假设】（为推进采用的默认，欢迎纠正）

1. 元数据化后**运营仍永不写 DRL**，只在**注册过的 schema 白名单**内拼条件树 → 受控翻译（安全红线不因元数据化退让，反而加固）。
2. 出行是**累积型但平台无状态**：`completedTrips` 等窗口聚合值由 **caller 预聚合后传入**，平台不做窗口/CEP，只对入参上下文做单次决策（与现有模型一致）。
3. 现金奖励等权益，平台**只返回「应发什么」，履约（发放、到账、幂等去重）在 caller 侧**（与电商折扣/赠品履约在电商侧同理）。
4. artifact/manifest/pointer/outbox/audit/审核/灰度机器**业务线无关，原样复用**，仅 key 增加 `tenant_id` 维度、发布单内容随类型不同。
5. MVP 租户由**平台管理员开通**；租户全自助 signup 放二期。
6. 计费 MVP 只做**计量 + 限额 + 用量看板**，出账/发票/对账/支付全二期。
7. benefit-type MVP 只做 **DISCOUNT / GIFT / CASH_REWARD** 三种覆盖两条验证线；更多类型走注册表二期扩。
8. 阶梯（LADDER）机制通用，**阈值字段可配**（orderAmount / completedTrips / …），沿用现有 `redPackageRangeAmount` JSON 分档结构（字段语义换掉）。
9. D1（NO_PROMOTION 降级 + 库存/预算仅展示不扣减）、D2（多级审核 + 强制职责分离 + 多维灰度 + A/B）**对所有业务线（含出行）继续生效**；出行的 NO_PROMOTION = 引擎故障不发奖，财务安全。
10. 决策上下文从「固定字段契约」改为「**按 bizLine schema 校验的动态键值包**」，`bizLine` 必填、`tenant` 从 API Key 推导或必填。
11. 租户隔离 MVP 为**逻辑隔离**（每表 `tenant_id` + 查询强制过滤），非物理/地域隔离。

### 9.2 【待澄清】（需用户拍板，按影响面排序）

1. **schema 值类型的范围**：MVP 除现有 NUMBER/STRING/ARRAY 外，**至少要加 ENUM（+候选值）**才能表达出行 `driverLevel/timeSlot/vehicleType`。是否还需 **BOOLEAN / DATE / GEO**？→ 直接决定元数据层与翻译器的类型矩阵工作量与前端下拉控件。（前端决策记录已标 field-dict 无 ENUM/候选值是缺口。）
2. **租户开通方式**：MVP 平台管理员手动开通够用，还是本期就要**自助 signup**？签约主体与「一个集团多 bizLine 共享账单」的账户模型如何映射？→ 决定 tenant 实体与身份/计费耦合度。
3. **schema 演进策略**：业务线 schema 上线后**要不要改字段**（加字段/改候选值/删字段）？改了历史 artifact（已冻结旧 schema 约束）如何兼容？→ 决定 schema 是否需要版本化、以及 artifact 与 schema 版本的绑定关系（可能是继 fact 重构后第二大架构点）。
4. **合并策略跨类型语义**：出行「多单奖励 + 阶梯奖励」同时命中时，STACK（累加）还是 MAX（取大）？跨 **不同 benefit-type**（如现金 + 赠品）能否合并、怎么合并？→ 现有 StackStrategy 是同类折扣金额语义，跨异构权益合并需明确定义。
5. **租户隔离强度与合规**：逻辑隔离（tenant_id 过滤）是否满足目标客户的合规要求？是否有**数据驻留/物理隔离/删除权**诉求？→ 决定 MVP 隔离是否够、二期是否必须物理隔离。
6. （次要）**计量口径与计费单元**：决策调用「成功含 fail-safe」是否都计费？dryRun/预览/影子调用是否计量？免费额度与阶梯如何分档？→ 决定计量埋点的口径。
7. （次要）**API Key 作用域粒度**：Key scope 到 tenant 还是 tenant+bizLine？一个租户多 bizLine 是一把 Key 还是多把？→ 决定鉴权与限流的粒度。
8. （次要）**「注册全新 benefit-type」的流程**：平台注册新类型是否需要独立审核/灰度（类似活动发布）？租户能否申请新类型进入平台待办？→ 决定平台扩展的治理流程。

## 10. 附：给架构 Agent 的三条承重产品约束（勿绕过）

1. **决策上下文必须元数据/Map 承载，且 M0 就位**：`ActivityRuleContext` 固定 getter → 通用 Map 承载 fact；`RuleField` 枚举 → 每 bizLine 注册的 `activity_context_schema` 数据；翻译器按注册 schema 生成约束并**对动态 schema 仍严格 fail-closed**。这是「零代码接业务线」的**唯一使能项**，晚做 10 倍成本。
2. **阶梯阈值字段可配 + benefit-type 抽象（DISCOUNT/GIFT/CASH_REWARD）+ 平台保持无状态**：LADDER 解绑 orderAmount；权益抽象为带载荷 schema 的 benefit-type，平台只判「应发什么」、履约在 caller；出行的窗口累积在 caller 侧完成，**平台不引 CEP/有状态**。这三条让电商与出行共用同一套机制。
3. **租户是最高隔离 key，全链路加 `tenant_id`**：`release_key=tenantId:bizLine`；每表 + artifact/manifest/pointer/decision-log/effect 加租户维度；每查询强制租户过滤；tenant 作指标 tag 需白名单硬上限。artifact/审核/灰度机器**协议不改**，只在 key 上加租户维度。任一处漏租户过滤 = 串租户 = SaaS 致命事故。
