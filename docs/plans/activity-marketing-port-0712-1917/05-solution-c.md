# 05 Solution C - 前端流程模拟器 + 最小后端规则沙箱

## architecture-designer 视角

### 架构

不迁移来源项目服务结构，只在当前 `CampaignService` 基础上扩展一个“活动创建流程模拟器”：

- 前端重做为报表式提交。
- 后端仍只保存一个活动主表或少量 JSON 字段。
- 商品绑定、规则详情、策略、资格条件都作为 JSON 存在一个扩展字段中。
- 执行时将 JSON 转为 DRL 或 Java 过滤器。

### 模块职责

- `CampaignEntity` 扩展字段或新增 `ActivityDraftEntity`。
- `CampaignService` 扩展为创建、预览、验证。
- 前端承担大部分表单与 JSON 组织。

### 核心流程

1. 前端填写活动表单。
2. 后端保存 JSON 草稿。
3. 前端点击验证时，后端生成一段 DRL 或执行 Java 条件过滤。
4. 返回规则命中结果。

### 改动范围

小。主要改当前 `Campaign*` 与静态前端。

### 扩展性

弱。能快速看交互，但无法准确评估来源项目五层数据、版本化、商品绑定、规则引擎接入点、灰度回滚等真实改造问题。

### 实施成本

低。

## risk-reviewer 视角

- 兼容性：风险最低。
- 事务：单表保存，简单。
- 并发：只需处理同活动覆盖。
- 性能：无法模拟真实 toC 查询性能。
- 安全：如果允许直接编辑 DRL，仍有风险；若只用 JSON 条件树风险较低。
- 数据迁移：几乎没有。
- 灰度与回滚：不能验证来源项目真实灰度链路。

## test-designer 视角

重点是前端表单和 JSON 校验，不适合覆盖真实架构风险。

## 结论

适合 1 到 2 天内验证 UI 交互想法，不适合作为“活动营销逻辑放一份并研究服务端改造”的最终方案。
