## 背景：这次重构的靶心

条件侧（准入）已经是数据驱动的闭环，权益侧（给什么）是硬编码的：

| | 条件侧 | 权益侧 |
|---|---|---|
| 后端元数据 | `RuleSchemaRegistry` 按 (tenant, bizLine) 解析字段白名单 | 无。`redPackage*` 四个字段直接长在 `ActivityCreateRequest` 顶层 |
| 下发契约 | `GET /activity-marketing/field-dict` | 无 |
| 前端渲染 | `ConditionLeaf.vue` 按 `valueType` / `operators` 动态渲染 | `EditorView.vue` 用 `v-if="dr.activityType===1"` 硬编码两套表单 |
| 求值 | `RuleConditionTranslator` 纯函数，零引擎耦合 | `ActivityDrlBuilder` 硬编码把 `redPackageAmount` 抄进 `computedAmount` |

**加一个玩法 = 改前端模板 + TS 接口 + 后端 record + JPA 实体 + DRL 生成器，五处齐动。**

条件侧是一个可复制的好样板。重构的核心命题是：**能不能把这个样板套到权益侧。**

## D1 · 先量成本，再决定是否上抽象（闸门优先于设计）

**决策**：在写任何重构代码之前，先做 1–2 人日的闸门——拿业务的 6 个月玩法清单 + 用现有硬编码方式实测「加第三个玩法」的真实人日。用结果决定走 S 档（最小版）还是 M 档（含行项模型）。

**备选方案 A（被否决）**：直接按玩法建模那一路的产出实施——21 个玩法 × 14 个能力原子的 IR + PlayTemplate + 编译器。

**否决理由**：该路线在自己的 `assumptions` 里承认「21 个玩法来自行业通行做法，**未从代码或文档中找到任何玩法需求清单**」。仓库里确实没有。而把 `COUPONS(2)` 按现有方式再加一遍是 60–100 行、约 1 人日；这套抽象要回本需要 15 个以上新玩法。**在没有清单的情况下，这笔账算不出来，投入就是赌博。**

**支撑数据**：五路合计提出 300+ 文件变更、40+ 个新 Java 类、5 张新表；而平台后端 main 仅 6096 行、测试 3145 行。**新增代码量是被改造系统的数倍**——这个比例本身就是警报。

**代价**：闸门会推迟正式开工 1–2 人日。接受。

## D2 · 三份评审冲突时的裁决原则

三个评审视角给出方向相反的结论：

- **工程可行性**：需求基线不存在，砍到 25–35 人日
- **业务覆盖度**：抽象是漏的，第N件M折 / 秒杀 / 加价购 / 裂变一个都配不出来，要**加**能力
- **前后端一致性**：五路给出 4 个名字、3 种主键、3 张表名，后端字典渲染不出前端任何一个表单

**决策**：**工程可行性赢在「做多少」，业务覆盖度赢在「诚实」，前后端一致性是前置条件。**

**理由**：这两份评审并不真的矛盾——它们说的是不同的事。

- 「抽象漏了」是对的，但漏的原因是需求不清，不是投入不够。**在需求不清时补能力，只会漏得更贵。**
- 业务覆盖度真正不可让步的那条不是「能力不够」，而是「**承诺与实现不符**」（见 D5）。这不是范围问题。

## D3 · 权益求值的闭集只留 FIXED / LADDER 两支

**决策**：`sealed interface BenefitValue permits Fixed, Ladder`。

**备选方案（被否决）**：五模式闭集 —— `Fixed` / `Ladder` / `RandomRange` / `Table`（多维查表）/ `Expression`（QLExpress + AST 白名单 + 指令集缓存）。

**否决理由**：

- `Table` / `Expression`：**没有任何现存或计划中的玩法需要它们**。`Expression` 单独就要引一个新运行时依赖 + 写一个 AST 白名单校验器 + 承担一类新的注入面。
- `sealed` 的价值恰恰是**以后加分支时编译期报错**，不需要提前占位。
- `RandomRange` 单独处理，见 D4。

## D4 · `RANDOM_AMOUNT` 按缺陷处理，不按字面语义迁移

**决策**：先跑 SQL 统计 `take_type=2` 的存量行数。为 0 → 把 `DistributionMode.RANDOM_AMOUNT` 枚举**删掉**；非 0 → 标 `NEEDS_REVIEW` 逐行人工裁决。

**备选方案（被否决）**：backfill 规则把 `take_type==2` 且恰好 1 档的行**自动转换**成 `RandomRange` 并实现随机金额。

**否决理由**：`DistributionMode.RANDOM_AMOUNT` 枚举存在但决策链路不存在，且 `redPackageRangeAmount` 字段已被阶梯语义占用——**运营真配了会被静默吞成 0 元**。自动转换会把今天实际发 0 元的存量行改成发随机金额，**这是在迁移里改钱**。

## D5 · 库存与频次：不允许维持「有字段、有写入、决策不读」

**决策**：二选一，本轮必须落地其中之一。**倾向 B。**

- **A · 真做**：新增 `activity_quota` 表 + 预占接口（RESERVE_THEN_CONFIRM，TTL 15 分钟）
- **B · 不做但说清楚**：控制台输入框置灰 + 悬浮提示「本期为声明式，决策不扣减」+ 创建响应回 `warnings` + 详情页 warn Banner

**倾向 B 的理由**：A 需要预占状态机 + TTL 回收 + 对账，量级接近整个 S 档；B 半天即可，且立刻消除「配了以为生效」这个真实的超发风险。等真有秒杀需求时再做 A。

**必须记录的冲突（五路原始提案无人处理）**：A 方案与既有架构不变量正面冲突——**`activity-decision` 连的是只读账号，物理上不能扣减**。所以预占写通道必须由 console 提供，决策命中后由调用方回调。任何「决策时扣库存」的设计都违反这条不变量。

**为什么这条不能推迟**：`inventory` / `userInventory` 读进 `ActivityCandidate` 后全仓零读取（已核实），`userInventory` 创建时恒为 0。运营配了「每人限领 1 次」「秒杀总量 500」，线上**无限超发**且界面不告知。这是诚实性问题，不是功能优先级问题。

## D6 · 影子双跑降级为 JUnit 级金标对拍

**决策**：取消生产形态（`@Primary` 装饰器 + 线程池 + 采样 + 在线比对），改为 `ParityTest`——读 40 例金标 fixture，新旧两条链路各跑一遍，比 `hitAmount`（用 `compareTo` 不用 `equals`）、`hitActivityId`、`strategy`、`gifts`（排序后比）。

**否决理由**：在线影子意味着 DB 查询翻倍 + 一个新线程池 + 采样逻辑 + 生产比对告警，而这里**还没有生产流量**。零风险的 JUnit 对拍能提供同等的等价性保证。等真有生产流量再评估。

## D7 · 快照包优先于分层引擎（修正上一份评估报告的排序）

**决策**：顺序改为 **权益模型 → 代际快照包 → 分层引擎**，且后两者拆成独立路线单独排期。

**被修正的原方案**：上一份架构评估报告把 P1-1 快照包、P1-2 阶梯移出规则、P1-3 QLExpress 后端**并列**在同一阶段。

**修正理由**：

- **快照包不改计算语义**，只改「昂贵动作发生在哪个线程」。解 D1/D3/D8/D9/D11，风险可控。
- **分层引擎改计算语义**（Drools → 表达式引擎 / Java 查表），风险最高、收益最不确定，且它的验证依赖金标集——**而金标集是 B0 才建的**，并列排会导致验证手段还没就位就动计算。

## D8 · schema 运维子系统整块推迟

**决策**：本轮只做「registry 落库 + 只读下发」，写入继续走代码发版。运维端点、审计表、影响面预演、四眼审批、前端 schema 编辑界面全部推迟。

**否决理由**：`RuleSchemaRegistry.register` 在主源码零调用、进程内 `ConcurrentHashMap`、无持久化——**它今天没有任何调用方，也就没有任何人受害**。在一个 stub 上外挂第二个管理产品，是把假需求做成真代码。

## D9 · 前端只允许新增一个 UI 原语

**决策**：新原语只保留 `DataTable`（`ListView` 已有手写实现要复用，也是保住 tablet / phone smoke 无横向溢出断言的关键手法）。`Drawer` / `Toggle` / `Stepper` 等到出现第二个使用点再抽。

**同时删除**：`useDraftAutosave`（localStorage 草稿 + baseVersion 比对 + 恢复 Banner + 冲突三态）、`draftDiff` 纯函数 + `DiffRow` 类型 + 单测。

**否决理由**：对象是一个 536 行的表单页。现有的「DOM 事件冒泡猜 dirty」确实丑，但 `JSON.stringify(draft) !== JSON.stringify(baseline)` 三行就解决，不需要一个带纯函数 + 单测 + 四处复用的 diff 子系统。

## D11 · `benefit_expression` 明确永不做

**决策**：拒绝「把权益计算写成表达式存进 DB」。接受边界：**新计算原语 = 一次性 Java 改动**。

**否决理由**：运营配置的一个字符串直接决定发多少钱，没有编译期检查、没有单测覆盖、出错只能在生产发现。「加玩法不改代码」这个目标不值得用「改钱不经过 code review」来换。

### D12-1 · 走 S 档（连带删除三个原子）

玩法只有金额型 → `BenefitValue` 闭集**只留 `FIXED` / `LADDER`**，`sealed` 保证以后加分支时编译期报错。

**连带动作（立即执行，不留「以后再说」）**：从设计里**删掉** `Selector`（行选择）、`Allocation`（分摊）、`UNIT_PRICE`（单价基数）三个原子，以及能力矩阵里 A4/A5/A9 三行。
`SpuDiscountRequest` **不加 `items[]`**——决策入参形状冻结，金标集直接按现形状录制。

若将来真出现单价类玩法（第二件半价 / 秒杀一口价 / 加价购），那是一次**明确的破坏性契约升级**，重新立项、重新估，不在本轮偷偷预留。

### D12-2 · 两条线并行（但必须先建共享地基）

用户选择并行。我此前提示过风险：两条线都会碰 `ActivityQueryService`——性能线改**数据来源**，权益线改**求值结构**，直接并行冲突面很大。

**裁决：接受并行，但插入两个共享前置，且两条线都不得在前置完成前动 `ActivityQueryService`。**

- **前置 1 · B0**（金标集 40 例 + 决策三指标 + `storeId`）——没有金标集，两条线都无法证明自己没改坏金额。
- **前置 2 · 接缝拆分**（纯搬移，行为不变，由金标集守住）：把 `ActivityQueryService` 沿它**已经存在**的接缝拆成三块——
  - `DecisionDataLoader`：取数（`boundActivityIds` / `filterBeginActivities` / `flatten` / `eligibilityDef` / `ladderDefs` / `resolveStrategy`）→ **性能线拥有**
  - `BenefitEvaluator`：求值（`evalEligibility` / `evalLadder` / `evalDiscount` / `legacyMax`）→ **权益线拥有**
  - `ActivityQueryService`：退化成薄编排

拆完之后两条线各改各的文件，冲突收敛到编排层那几十行。**这一步是并行的前提，不是可选优化。**

### D12-4 · `storeId` 加入参，不删白名单

代码证据（已逐行核实）：

| 位置 | 事实 |
|---|---|
| `DemoProductEntity.storeId` | 商品属于哪个店铺 |
| `ActivitySpuBindingEntity.storeId` | 绑定带店铺 |
| `ActivityCreateRequest.SpuBinding(storeId, spuId)` | 写侧契约有它 |
| `EditorView.vue:416` | 前端有「店铺ID」输入列 |
| `RuleSchemaRegistry:116` | 白名单里有「店铺」 |
| `SpuDiscountRequest` | **唯独决策入参没有** |

即**写侧完整建模了店铺，只有决策入参漏了**。删白名单等于砍掉系统其它部分已建好的能力。

语义判定：该字段在白名单里与 `orderAmount` / `quantity` / `userDistrictId` / `userTags` / `spuId` 并列，全是**订单/用户上下文**，故「店铺」= 这单来自哪个门店，不是「活动绑在哪个店」。

实现要求（不只是补一个字段）：
1. `SpuDiscountRequest` 增 `storeId`——纯增量，老调用方不传 → null → fail-closed，与今天行为一致。
2. `buildContext` 改为**由一张唯一映射表驱动**，不再手写六行 `putAttr`。顺带解掉「新增条件字段还要改 Java」。
3. 加结构守卫：**白名单里每个 key 都必须在映射表里有来源**，缺一个即测试失败。反向的漏（`userId` 写进了属性袋却不在白名单里）保留但注明。

### D12-6 · 异构权益合并口径：本轮不裁决

原问题是「`spuDiscount` 只捞红包、`buyAndGetGifts` 只捞买赠，合并后默认全局单选还是按类型分桶全给——两个默认值差一个数量级的发放金额」。

S 档下**两条通路仍然物理隔离，不发生合并**，因此这个默认值本轮无处生效。现在拍一个用不上的值，只会在真要合并时被当成「已经定过的」而不再复核。**等真要合并时再拍，并列为该批次的准入前提。**
