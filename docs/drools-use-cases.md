# Drools 应用场景与定位

> 活文档。最后核对：2026-08-28；选型判断与当前 Step 1–24 能力范围一致。
>
> 常见误区："Drools 是不是一般跟营销活动平台一起用？"
> 不完全对。营销是 Drools 的**常客**，但不是它的**绑定关系**。本文澄清 Drools 的真实定位，
> 配合 `docs/drools-capabilities.md`（能力全景）、`docs/drools-vs-aviator.md`（选型对照）一起看。

## "营销平台 + 规则引擎" 这个印象怎么来的

合理——因为**营销/活动场景恰好是规则引擎的甜区**，也最适合作为规则能力主线（本仓库 Step 2/3/4/7 覆盖折扣、VIP、购物车满减）。这类场景命中了规则引擎的全部价值点：

- 规则**多、碎、还经常变**（每个大促一套玩法）
- 改规则的人**不想动代码 / 不想发版**（运营、业务方）
- 规则之间**会叠加、会冲突**，需要优先级仲裁（本项目的 `salience`、决策表）

所以"营销活动平台 + 规则引擎"是个很自然的组合。但这是 Drools 的一个**应用场景**，不是它的**定位**。

## Drools 的真实定位

Drools 是个**通用业务规则引擎（BRMS）**，营销只是它众多落地领域之一。其它高频领域：

| 领域 | 典型规则 | 本仓库对应 |
| --- | --- | --- |
| **风控 / 反欺诈** | 交易拦截、滑窗突发检测、黑名单命中 | Step 4（not/exists）、Step 8（CEP 滑窗），金融领域用得极重 |
| **保险** | 核保、理赔自动判定、保费计算 | Step 17（DMN 是保险/信贷常用标准） |
| **信贷审批** | 授信额度、利率定价、准入规则 | Step 7 决策表 + Step 17 DMN 决策链 |
| **医疗** | 诊疗路径、用药冲突检测 | — |
| **供应链 / 物流** | 调度、配载、合规校验 | — |
| **电信计费** | 套餐资费、优惠叠加 | Step 2 规则叠加同构 |
| **营销 / 活动** | 折扣、满减、VIP 档位、发券 | Step 2/3/4/7（本仓库活动规则主线） |

## 一个更准确的说法

> Drools 适合**"规则频繁变化、需要和代码解耦、由业务方维护、规则间存在复杂组合/优先级"**
> 的任何决策场景。营销活动平台是其中一个非常典型、但远非唯一的场景。

## 什么时候**不该**上 Drools

反过来说，如果规则**很少变、逻辑简单**，硬上 Drools 反而是过度设计——直接 `if-else`
或一个轻量表达式引擎（见 `docs/drools-vs-aviator.md`）更划算。判断信号：

- 规则就是几个**独立的布尔/数值表达式**，彼此不联动 → 表达式引擎（Aviator/QLExpress/SpEL）
- 规则**几乎不变**、跟代码一起发版没痛点 → 直接写 Java
- 规则**少、fact 少**，又对冷启动/部署足迹敏感 → RETE 的增量匹配优势发挥不出来，Drools 反而更慢更重

## 结论

营销平台是 Drools 的常客，但 Drools 不是"营销平台专用件"。它的本质是
**把易变的决策逻辑从应用代码里抽出来，交给引擎和业务方共同维护**——
凡是符合这个特征的决策场景（风控、保险、信贷、计费、营销……）都是它的舞台。
